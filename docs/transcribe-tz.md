## 1. Назначение и область действия

### 1.1. Назначение

Подсистема принимает записи телефонных звонков в формате WAV двумя
способами — локальная мультизагрузка и импорт из личного кабинета
Twin24 — асинхронно прогоняет каждую запись через двухстадийный
OpenAI-пайплайн (транскрибация + разметка ролей Оператор/Клиент) и
выдаёт единый XLSX-файл «ID диалога / Текст транскрибации». Данные
живут ограниченное время (TTL 24 ч) и удаляются после выдачи результата
или по TTL.

### 1.2. Границы и классификация

| Аспект | Решение |
|--------|---------|
| **Классификация** | Самостоятельная (standalone) подсистема. **Не** модуль `testing`. |
| **Размещение** | Поддомен `transcribe.bot-atelier.ru`. |
| **Имя и идентификаторы** | slug `transcribe`; название «Транскрибация звонков»; контейнер `transcribe-app`; docker-volume `transcribe-data`; рабочая cookie `transcribe_ws`; серверный каталог `/opt/transcribe`. |
| **Связь с экосистемой** | Только SSO: общая cookie `session_id` + внутренний endpoint `testing` `GET /api/internal/session`. Никаких `projects`, `bots`, `project_members`, `issues`, БД `testing`, сервисов и страниц `testing` не используется. Код других подсистем не импортируется. |
| **Соответствие правилу AGENTS.md §1.2** | Исключение из проектной модели (доступ всем активным пользователям без проектной изоляции) фиксируется архитектурным документом `.opencode/architecture/transcribe.md` как «самодостаточный рабочий стол с ограниченным временем жизни (TTL)». |

### 1.3. Целевая аудитория и доступ

Любой активный пользователь экосистемы (роли `admin`, `tester`,
`developer`, `manager`) после прохождения SSO. Роли внутри подсистемы не
различаются и не показываются. Идентичность пользователя внутрь
подсистемы не передаётся (шлюз только проверяет валидность сессии).

### 1.4. Сценарий использования (один поток)

Добавить WAV (локально и/или из Twin24) → дождаться терминальных
статусов у всей пачки → скачать единый Excel → покинуть подсистему
(через анкер «← На главную», без выхода из аккаунта).

## 2. Функциональные требования

### 2.1. Сценарий А: локальная мультизагрузка `.wav`

| Требование | Спецификация |
|------------|--------------|
| **Формат файлов** | Только `.wav` (расширение проверяется регистронезависимо). |
| **Размер одного файла** | ≤ 25 МБ (жёсткий лимит API OpenAI — **проверить актуальность** перед девом). |
| **Число файлов** | ≤ 50 файлов на workspace. |
| **Общий объём** | ≤ 1 ГБ аудио на workspace (сумма `size_bytes` всех файлов workspace). |
| **Идентификатор** | `dialog_id` = имя файла без расширения (как есть, без нормализации). |
| **Дубликаты** | `UNIQUE (workspace_id, dialog_id)` — повторное имя отклоняется с ошибкой по конкретному файлу, остальные принимаются. |
| **Транспорт** | UI шлёт файлы последовательными `POST /api/files` (один файл на запрос) — естественный per-file прогресс и ошибки. |
| **Валидация** | Сервер перепроверяет все ограничения; отказ по одному файлу не блокирует остальные. Клиент показывает ошибки в очереди загрузки с кнопкой «Повторить». |

### 2.2. Сценарий Б: импорт из ЛК Twin24

#### 2.2.1. Логин

- **Endpoint Twin24:** `POST https://twin24.ai/iam/api/v1/auth/login`
- **Тело запроса:** `{ email, password, ttl: 86400 }`
- **Ответ:** `{ token, refreshToken }` (`refreshToken` живёт до 1 года).
- **Хранение:** токен и refreshToken — **только в оперативной памяти процесса** (dict, ключ — `workspace_id`). Пароль не сохраняется и не логируется; поле формы очищается после отправки.
- **TTL логина:** всегда 86400 (фиксировано, у пользователя не спрашиваем).
- **Авто-refresh:** (1) проактивно — перед вызовом, если `now ≥ expires_at − 60 с`; (2) реактивно — при `401` от Twin24 (один повтор через refresh).
- **Контракт refresh [внешний вопрос: проверить]:** предполагается
  `POST /iam/api/v1/auth/refresh { refreshToken } → { token, refreshToken }`.
- **Рестарт контейнера:** словарь токенов пуст; UI показывает «Twin24 не
  подключён»; уже скачанные WAV и результаты в БД не теряются; для
  добавления новых диалогов требуется повторный логин.

#### 2.2.2. Импорт строк (UUID и/или ссылки)

- **Ввод:** textarea, формат — **построчно** (один UUID или одна ссылка
  на строку). Пустые строки и хвостовые пробелы молча игнорируются.
- **Парсинг на сервере:**
  1. Ссылка `^https://twin24\.ai/app/download/records/<UUID>/?$` →
     извлекается UUID.
  2. «Голый» UUID — регэксп
     `[0-9a-fA-F]{8}-[0-9a-fA-F]{4}-[0-9a-fA-F]{4}-[0-9a-fA-F]{4}-[0-9a-fA-F]{12}`.
  3. Иначе — строка в `rejected` с причиной («не похоже на UUID или
     ссылку Twin24»).
- **Нормализация:** UUID приводится к нижнему регистру.
- **Дубликаты:** ссылка и «голый» UUID одного и того же диалога — один
  `dialog_id`; второй вариант отклоняется («дубликат: диалог уже в
  пачке»).
- **Лимит на запрос:** ≤ 50 строк за один `POST /api/twin24/import`.
- **Ответ:** `{ accepted: [{uuid, file_id}], rejected: [{line, reason}] }`.
  Принятые строки уходят в `queued`; отклонённые остаются в textarea
  для правки.
- **Если Twin24 не подключён:** `409 Conflict`.

#### 2.2.3. Скачивание WAV из Twin24

- **Endpoint [внешний вопрос: уточнить перед разработкой]:** ожидается
  `GET https://twin24.ai/app/download/records/{UUID}/` с заголовком
  авторизации Twin24; формат ответа — WAV (без конвертации).
- **Заголовки авторизации [внешний вопрос: уточнить]:** ожидается
  `Authorization: Bearer <token>` или эквивалент.
- **Момент:** выполняется воркером в начале стадии `transcribing`
  (для пользователя — «транскрибируется»).
- **Неудача скачивания / 401-после-refresh:** файл переводится в
  `error` с причиной «Не удалось скачать диалог из Twin24: …»; пачка
  продолжает обрабатываться.
- **Формат файла:** ожидается WAV. Если получен не WAV — в v1 это
  ошибка по файлу; конвертация вне скоупа v1.

### 2.3. Пайплайн обработки (на файл)

| Стадия | Модель | Параметры | Результат |
|--------|--------|-----------|-----------|
| 1. Скачивание (только twin24) | — | таймаут/повторы — как у OpenAI-стадии ниже | WAV в `/data/work/<ws>/audio/<file_id>.wav` |
| 2. Транскрибация | `gpt-4o-transcribe` (`/v1/audio/transcriptions`) | таймаут попытки **30 с**; первая попытка + до **3 повторов**; паузы **2/4/6 с** | сырой текст → столбец `transcript` в БД (промежуточное хранилище, удаляется после выдачи) |
| 3. Разметка ролей | `gpt-4o-mini` (chat.completions) | `temperature=0`; те же повторы; системный промпт — Приложение А | `result_text` в БД (формат «Оператор: … / Клиент: …» строго построчно); статус → `done` |

- **Параллелизм:** 3–5 одновременных запросов к OpenAI (env
  `TRANSCRIBE_WORKERS`, по умолчанию 4, кламп [3, 5]).
- **Порядок:** FIFO внутри очереди.
- **Финальная неудача (все повторы провалились):** файл → `error` с
  причиной («транскрибация не удалась после 3 повторов: …» /
  «разметка ролей не удалась…»).
- **Промежуточное хранилище (ТЗ №2 черновика):** столбец `transcript` в
  БД, записывается немедленно по завершении стадии 2; служит точкой
  восстановления при рестарте (стадия 2 не повторяется).

### 2.4. Статусная модель

| Статус | Русская метка UI | Терминальный? |
|--------|-------------------|----------------|
| `queued` | В очереди | нет |
| `transcribing` | Транскрибируется | нет |
| `labeling` | Размечаются роли | нет |
| `done` | Готово | да |
| `error` | Ошибка | да |

- Переходы строго по порядку (`queued → transcribing → labeling →
  done|error`); обратных переходов нет.
- Скачивание из Twin24 — подшаг стадии `transcribing`.
- **`all_terminal`:** в workspace ≥1 файла и все файлы имеют статус
  `done` или `error`. Только в этом состоянии доступна кнопка
  «Скачать результат (Excel)». Частичные ошибки не блокируют выдачу.

### 2.5. Результат: XLSX

- **Библиотека:** `openpyxl`.
- **Структура:** один лист; шапка «ID диалога» / «Текст транскрибации».
- **Колонка A (`dialog_id`):** принудительно текстовый формат ячейки
  (`number_format = '@'`) — защита UUID и числоподобных имён файлов от
  автопреобразования Excel в экспоненциальную запись.
- **Колонка B (`result_text`):** размеченный текст; при статусе `error` —
  строка вида «ОШИБКА: <причина>». Одна строка XLSX = один файл.
- **Порядок строк:** порядок добавления файлов в пачку.
- **Имя файла:** `transcribe-<ГГГГММДД>-<ЧЧММСС>.xlsx`,
  `Content-Disposition: attachment`.
- **Хранение:** XLSX **не** сохраняется на диске — генерируется из БД
  при каждом запросе `GET /api/export` и отдаётся стримом. Повторное
  скачивание регенерируется из `result_text` (живёт до TTL).
- **Доступность кнопки:** при `all_terminal`. Появление раньше —
  запрещено.

### 2.6. Явный сброс рабочего стола — «Начать новую пачку» (v1)

- **API:** `POST /api/reset`.
- **Эффект:** удаляет все `files` workspace, все WAV на диске, все
  `result_text`; обновляет `workspaces.last_seen_at` и сбрасывает
  `delivered_at = NULL` (TTL-таймер начинается заново). Сам
  `workspace_id` (cookie) сохраняется.
- **Twin24-подключение:** **не** сбрасывается (токены остаются в RAM).
- **UI:** кнопка «Начать новую пачку» в шапке карточки «Пачка» с
  модальным подтверждением («Все текущие файлы и результаты будут
  удалены. Twin24-подключение сохранится.»).
- **Доступность:** при непустом workspace; после сброса — пустое
  состояние (§6.3.1).

### 2.7. Поля `/api/state` для UI (v1)

- **`expires_at`:** ISO-8601 время срабатывания TTL (позволяет UI
  показывать «ещё 19 ч» вместо качественного «24 часа»).
- **`used_bytes`:** суммарный объём WAV workspace (для индикатора
  «X из 1 ГБ»).

## 3. Архитектура

### 3.1. Классификация и топология

```
Браузер
  │  https://transcribe.bot-atelier.ru
  ▼
nginx (TLS, SSO-шлюз)
  │ 1) auth_request ──▶ GET http://127.0.0.1:3000/api/internal/session
  │                     Cookie: session_id=… + X-Internal-Auth: <секрет>
  │ 2) 200 → proxy_pass
  ▼
transcribe-app (127.0.0.1:8082; в контейнере :8080)
  ├─ HTTP API + статика UI           (FastAPI + uvicorn)
  ├─ asyncio-очередь + 3–5 воркеров ─▶ OpenAI (gpt-4o-transcribe,
  │                                     gpt-4o-mini) и Twin24
  ├─ SQLite /data/transcribe.db      (volume transcribe-data)
  ├─ WAV /data/work/<ws>/            (volume transcribe-data)
  └─ TTL-GC (каждые 10 мин) + boot-recovery очереди
```

### 3.2. Стек

| Компонент | Выбор | Обоснование |
|-----------|-------|-------------|
| Язык | Python 3.12 | openai, openpyxl, httpx — нативные библиотеки |
| Web-фреймворк | FastAPI + uvicorn | штатный multipart, StaticFiles, async; допустим aiohttp-эквивалент |
| HTTP-клиент | `httpx` (async) | для OpenAI и Twin24 |
| OpenAI-клиент | `openai` (официальный) | |
| XLSX | `openpyxl` | текстовый формат ячеек |
| БД | SQLite (WAL) | лёгкая персистентность без внешних сервисов |
| Базовый образ | `python:3.12-slim` | |
| ffmpeg | **не нужен** | WAV передаётся в OpenAI как есть |

### 3.3. Рантайм

- **Один Docker-контейнер** `transcribe-app` с in-process
  asyncio-очередью. Redis/Celery **не** вводятся (Redis в экосистеме
  нет, операционная сложность не оправдана для пачек в десятки файлов).
- **Публикация порта:** `127.0.0.1:8082` → `:8080` в контейнере.
- **Процесс-менеджер:** Docker `restart: unless-stopped`; PM2 **не**
  используется.

### 3.4. Структура репозитория

```text
transcribe/
  app/                        # исходники подсистемы
    web_app.py                # HTTP API, статика UI, asyncio-очередь, воркеры

    twin24.py                 # клиент Twin24: login / refresh / download
    storage.py                # SQLite, файлы workspace, TTL-GC, boot-recovery
    xlsx.py                   # XLSX (текстовый формат ячеек)
    static/index.html         # UI без сборки (inline CSS/JS, без CDN)
    requirements.txt
    Dockerfile                # python:3.12-slim
    tests/                    # UUID-парсер, повторы, XLSX-формат, GC, статусы
  deploy/                     # артефакты выката
    nginx.conf                # server-блок: ССО-шлюз + proxy 127.0.0.1:8082
    docker-compose.yml        # transcribe-app + volume transcribe-data
    deploy.sh                 # по образцу audio-correction/deploy/deploy-mvp.sh
    DEPLOY.md                 # DNS, certbot, health-check, rollback
```

На сервере: `/opt/transcribe/` (`app/` + `deploy/`) и
`/opt/transcribe/.env` (`OPENAI_API_KEY`, chmod 600, **в git не
попадает**).

## 4. Модель данных и состояния

### 4.1. Персистентность

**Лёгкая персистентность (TTL-модель).** Состояние задач и результаты —
SQLite в docker-volume; WAV — в том же volume; токены Twin24 —
**исключительно в оперативной памяти процесса**. Модель отклоняется от
буквы «эфемерный рабочий стол» (AGENTS.md §1.2) в сторону «самодостаточного
рабочего стола с ограниченным временем жизни»; отклонение фиксируется
архитектурным документом `.opencode/architecture/transcribe.md` §2.1.

### 4.2. Идентификаторы и изоляция

- `workspace_id` = cookie `transcribe_ws` (`uuid4().hex`, 32 hex);
  создаётся лениво при первом обращении.
- `file_id` = `uuid4`.
- `dialog_id`: для Twin24 — UUID (нормализация к нижнему регистру);
  для локальной загрузки — имя файла без расширения.
- Workspace **не** привязан к идентичности пользователя (шлюз её не
  передаёт). Идентичность в подсистеме неизвестна.

### 4.3. Схема SQLite

Файл `/data/transcribe.db`, режим WAL.

**`workspaces`:**
| Столбец | Тип | Описание |
|---------|-----|----------|
| `id` | TEXT PK | = `workspace_id` (cookie) |
| `created_at` | INTEGER | UNIX-ts создания |
| `last_seen_at` | INTEGER | UNIX-ts последнего API-запроса (обновляется каждым запросом) |
| `delivered_at` | INTEGER NULL | UNIX-ts первой успешной выдачи XLSX (триггер очистки WAV) |

**`files`:**
| Столбец | Тип | Описание |
|---------|-----|----------|
| `id` | TEXT PK | `file_id` |
| `workspace_id` | TEXT FK | → `workspaces.id` |
| `dialog_id` | TEXT | UUID / имя файла |
| `source` | TEXT | `upload` \| `twin24` |
| `status` | TEXT | `queued` \| `transcribing` \| `labeling` \| `done` \| `error` |
| `error` | TEXT NULL | текст причины ошибки |
| `transcript` | TEXT NULL | сырой текст стадии 2 (удаляется после выдачи) |
| `result_text` | TEXT NULL | размеченный итог (живёт до TTL) |
| `audio_path` | TEXT NULL | относительный путь WAV (NULL после очистки) |
| `original_name` | TEXT NULL | исходное имя файла (только для `upload`) |
| `size_bytes` | INTEGER | размер WAV |
| `created_at` | INTEGER | |
| `updated_at` | INTEGER | |

**Индексы и ограничения:**
- `UNIQUE (workspace_id, dialog_id)` — защита от дубликатов.
- `INDEX (workspace_id, status)` — для запросов `all_terminal` и
  boot-recovery.

### 4.4. Файлы на диске (volume `transcribe-data`)

```text
/data/
  transcribe.db
  work/<workspace_id>/
    audio/<file_id>.wav     # исходный WAV (оба сценария)
```

- Имя на диске = `file_id`; оригинальное имя (для загрузки) — в БД.
- XLSX на диске **не** хранится (§2.5).
- В отличие от эфемерного MVP, путь детерминирован — `/data/work/<ws>/` —
  чтобы переживать рестарт и находиться из БД.

### 4.5. Токены Twin24 (только RAM)

```python
# in-process dict, НЕ в БД, НЕ на диске, НЕ в логах
TWIN24: dict[workspace_id → {email, token, refresh_token, expires_at}]
```

- `ttl` логина = 86400 (фикс.).
- Авто-refresh: проактивно (`now ≥ expires_at − 60 с`) и реактивно (по
  `401` от Twin24, один повтор).
- Рестарт контейнера → словарь пуст; UI «Twin24 не подключён»; уже
  скачанные WAV и результаты не теряются.

### 4.6. Очередь и воркеры

- **Структура:** `asyncio.Queue` + пул задач-воркеров.
- **Размер пула:** `TRANSCRIBE_WORKERS` (по умолчанию 4, кламп [3, 5]).
- **Одна задача = один файл:** `[download] → transcribe → label`.
- Параллелизм запросов к OpenAI = размеру пула.
- **Терминальные состояния:** `done`, `error`.

### 4.7. Очистка и TTL

| Событие | Действие |
|---------|----------|
| **Первая успешная выдача XLSX** | Ставится `workspaces.delivered_at`. Немедленно удаляются все WAV (`audio_path` → NULL, файл на диске удаляется) и промежуточные `transcript` (→ NULL). `result_text` и `dialog_id` остаются до TTL — повторное скачивание работает. |
| **TTL-GC (каждые 10 мин)** | Workspace с `last_seen_at < now − 24 ч` удаляется целиком (строки `files`, строка `workspaces`, каталог `/data/work/<ws>`). |
| **Явный сброс** (`POST /api/reset`) | Удаление всех `files` workspace, WAV и результатов; `workspace_id` сохраняется. |

### 4.8. Boot-recovery (поведение при рестарте)

| Объект | Где живёт | Рестарт контейнера / деплой |
|--------|-----------|------------------------------|
| Токены Twin24 | RAM | сбрасываются → UI «переподключите Twin24» |
| In-process очередь | RAM | восстанавливается из БД при старте |
| Состояния задач, результаты | SQLite (volume) | сохраняются |
| WAV | volume | сохраняются (до выдачи/TTL) |

**Boot-recovery при старте процесса:**
- Файлы со статусами `transcribing`/`labeling` переводятся в `queued` и
  пере-ставятся в очередь (с дедупликацией по `file_id`).
- Если `transcript` уже сохранён — стадия 2 пропускается, файл сразу
  идёт в разметку (экономия вызовов OpenAI).
- Ошибки «обработка прервана — добавьте файл заново» не генерируются:
  state-resume покрывает сценарий.

### 4.9. Что видит вернувшийся пользователь

- **Тот же браузер, до TTL:** свою пачку со статусами и результатами;
  кнопка Excel при `all_terminal`. Twin24-подключение сброшено только
  если был рестарт контейнера.
- **После TTL (24 ч без активности):** пустой рабочий стол (cookie
  остаётся, но workspace удалён — создастся новый при первом запросе).
- **Другой браузер / устройство:** новый пустой workspace (следствие
  SSO-шлюза, который не передаёт идентичность).
- **Переход «На главную» и возврат:** ничего не удаляют; `session_id`
  и `transcribe_ws` сохраняются.

## 5. API

### 5.1. Сводка эндпоинтов

| Метод | Путь | Назначение |
|-------|------|------------|
| `GET` | `/` | UI (`static/index.html`) |
| `GET` | `/api/health` | Health-check для deploy-скрипта (loopback) |
| `GET` | `/api/state` | Состояние workspace: файлы, Twin24, `all_terminal`, лимиты, TTL, объём |
| `POST` | `/api/files` | Загрузка одного WAV (multipart, поле `file`) |
| `POST` | `/api/twin24/login` | Логин в Twin24 |
| `POST` | `/api/twin24/import` | Импорт строк (UUID/ссылки) |
| `GET` | `/api/export` | Скачивание XLSX |
| `POST` | `/api/reset` | Явный сброс workspace («Начать новую пачку») |

Все endpoint (кроме `/api/health`) ключуются cookie `transcribe_ws`
(создаётся лениво при первом обращении). Наружу — только через
nginx-шлюз.

### 5.2. Детали

#### `GET /api/health`
- **Ответ:** `200 {"status": "ok"}`.
- **Назначение:** health-check deploy-скрипта; loopback-only.

#### `GET /api/state`
- **Ответ:**
  ```json
  {
    "files": [
      {
        "id": "<file_id>",
        "dialog_id": "<UUID | имя>",
        "source": "upload|twin24",
        "status": "queued|transcribing|labeling|done|error",
        "error": null,
        "size_bytes": 12345678
      }
    ],
    "twin24": { "connected": true, "email": "user@company.ru" },
    "all_terminal": true,
    "limits": {
      "max_file_bytes": 26214400,
      "max_files": 50,
      "max_workspace_bytes": 1073741824
    },
    "used_bytes": 123456789,
    "expires_at": "2026-09-20T14:32:00Z",
    "file_count": 12
  }
  ```
- **Polling:** UI опрашивает каждые 3 с, пока есть нетерминальные файлы;
  после `all_terminal` — останавливается, возобновляется при добавлении
  новых.

#### `POST /api/files`
- **Вход:** `multipart/form-data`, поле `file` (один WAV).
- **Проверки:** расширение `.wav` (регистронезависимо), размер
  ≤ 25 МБ, лимит 50 файлов, лимит 1 ГБ, дубликат `dialog_id`.
- **Ответы:**
  - `201` — `{ id, dialog_id, status: "queued" }`.
  - `400` — неверный формат / расширение / дубликат (с причиной).
  - `413` — размер > 25 МБ или превышен объём workspace.

#### `POST /api/twin24/login`
- **Вход:** `{ "email": "user@co.ru", "password": "…" }`.
- **Ответ:** `200 { "connected": true, "email": "user@co.ru" }`.
- **Ошибки:**
  - `401` — неверный email/пароль Twin24.
  - `502` — Twin24 недоступен.
- Пароль очищается из памяти сразу после использования; не логируется.

#### `POST /api/twin24/import`
- **Вход:** `{ "lines": "uuid1\nhttps://twin24.ai/app/download/records/uuid2/\n…" }`.
- **Ответ:** `200 { accepted: [{uuid, file_id}], rejected: [{line, reason}] }`.
- **Ошибки:**
  - `409` — Twin24 не подключён (нет токенов в RAM).
  - `400` — пустой ввод / > 50 строк.

Запрос с более чем 50 строками отклоняется целиком с кодом 400;
обработка валидных строк частично не выполняется.

#### `GET /api/export`
- **Условие:** `all_terminal = true` и `file_count ≥ 1`.
- **Ответ:** `200` `application/vnd.openxmlformats-officedocument.spreadsheetml.sheet`,
  `Content-Disposition: attachment; filename="transcribe-YYYYMMDD-HHMMSS.xlsx"`.
- **Побочный эффект:** первая успешная выдача ставит
  `workspaces.delivered_at` и запускает очистку WAV/`transcript` (§4.7).
- **Ошибки:** `409` — если `all_terminal = false`.

#### `POST /api/reset`
- **Эффект:** удаляет все `files` workspace, WAV на диске, `result_text`,
  `transcript`; `workspaces.last_seen_at` обновляется, `delivered_at`
  сбрасывается в NULL; cookie и Twin24-токены сохраняются.
- **Ответ:** `200 { "ok": true }`.
- **Ошибки:** нет (idempotent).

### 5.3. Cookie

| Cookie | Кто ставит | Назначение | Атрибуты |
|--------|-----------|------------|----------|
| `session_id` | `testing` | аутентификация в экосистеме | `Domain=.bot-atelier.ru`, `HttpOnly`, `Secure`, `SameSite=Lax` |
| `transcribe_ws` | `transcribe-app` | рабочий workspace (**не** аутентификация) | host-only, `HttpOnly`, `Secure`, `SameSite=Lax`, 32 hex |

Cookie независимы. Шлюз не создаёт и не удаляет `transcribe_ws`.

| Тип | Место | Вид |
|-----|-------|-----|
| Ошибка поля (логин Twin24) | под полем/формой | красный текст, поле остаётся заполненным |
| Ошибка строки (валидация импорта) | сводка панели Б | цитата строки + причина |

#### 6.3.6. Поведение в особых ситуациях

- **Нет связи / 503 шлюза (открытая вкладка):** баннер в «Пачке»;
  поллинг продолжает попытки; ввод формально возможен, но любые
  действия завершаются локальной ошибкой. Отдельного in-app экрана 503
  нет (nginx не отдаёт статику при недоступном `testing`).
- **Возврат в закрытую вкладку:** рабочий стол восстанавливается из
  `transcribe_ws`; Twin24-подключение могло сброситься — панель Б
  показывает состояние «сброшено».
- **Очистка по TTL:** возврат к пустому столу; нейтральная заглушка;
  без отдельного экрана «данные удалены».
- **Две вкладки с одной cookie:** один и тот же стол; обе поллят и
  сходятся к одному состоянию, конфликтов нет.

## 8. Доступ и безопасность

### 8.1. SSO-шлюз nginx

Дословно по образцу `correction-audio`:

- Общая cookie `session_id` (`HttpOnly`, `Secure`, `SameSite=Lax`,
  `Domain=.bot-atelier.ru`) ставит `testing`.
- nginx поддомена на **каждый** запрос выполняет `auth_request` к
  `testing: GET /api/internal/session` (loopback `127.0.0.1:3000`,
  заголовок `X-Internal-Auth: <INTERNAL_AUTH_TOKEN>`) и пропускает
  запрос к приложению (`127.0.0.1:8082`) только при `200`.

**Поток запроса:**

| Код внутреннего endpoint | Поведение nginx |
|--------------------------|-----------------|
| `200` | `proxy_pass` на `127.0.0.1:8082` |
| `401` | `302` на `https://bot-atelier.ru/login?next=https%3A%2F%2Ftranscribe.bot-atelier.ru%2F` |
| `403` | **явный `403 Forbidden`** (без редиректа; деактивированный аккаунт или неверный секрет шлюза не лечатся повторным входом) |
| `5xx` / `testing` недоступен | `503` (недоступны и новые, и уже открытые вкладки — проверка на каждый запрос) |

**Бэкпорт-задание (внешний артефакт, вне скоупа реализации transcribe):**
исправить nginx-блок `correction-audio`, где сейчас
`error_page 401 403 = @sso_login` (редирект на логин при обоих кодах),
чтобы привести его к той же семантике: `401` → редирект, `403` → явный
Forbidden. Задача регистрируется отдельно; в этом ТЗ — только как
согласованное требование к шлюзам экосистемы.

### 8.2. Секреты

| Секрет | Где хранится | Как подаётся |
|--------|--------------|--------------|
| `OPENAI_API_KEY` | `/opt/transcribe/.env` (chmod 600, не в git) | env контейнера |
| `INTERNAL_AUTH_TOKEN` | `/root/.internal_auth_token` на сервере + `.env.production` testing | sed-подстановка в nginx-шаблон при выкате |
| Пароль Twin24 | **нигде не хранится** | один POST-запрос; не сохраняется и не логируется |
| `token`/`refreshToken` Twin24 | только RAM процесса | очищается при рестарте контейнера |

### 8.3. Логирование внешних вызовов

- **Что логируется (stdout → `docker logs`):** метод, путь, HTTP-статус,
  длительность, размер, номер попытки, `workspace_id`, `file_id`, тело
  ошибки (без токенов).
- **Запрещено логировать:** пароль Twin24, `token`/`refreshToken`,
  заголовок `Authorization`, `OPENAI_API_KEY`, содержимое транскриптов и
  аудио, содержимое тел запросов с PII.

### 8.4. Изоляция workspace

- Все API-запросы ключуются cookie `transcribe_ws` (32 hex, host-only,
  `HttpOnly`, `Secure`).
- Без cookie доступ к чужому `file_id` / `workspace_id` невозможен.
- Идентичность пользователя экосистемы в подсистеме неизвестна
  (осознанное ограничение SSO-шлюза, как у `correction-audio`).

### 8.5. Конфиденциальность звонков (PII)

- Содержимое звонков не логируется.
- Аудио и тексты живут ≤ TTL.
- WAV удаляются после первой выдачи XLSX.
- Workspace полностью очищается по TTL 24 ч или явно (`POST /api/reset`).

### 8.6. Стоимость OpenAI

- Лимиты файла/пачки/объёма (§2.1, §2.2).
- Параллелизм 3–5.
- Повторы ≤ 3 с паузами 2/4/6 с.
- Stage-resume после рестартов (§4.8): сохранённый `transcript`
  пропускает стадию 2, экономит вызовы.

### 9.4. nginx-блок (`deploy/nginx.conf`)

```nginx
server {
    listen 80;
    server_name transcribe.bot-atelier.ru;

    # Один WAV ≤ 25 МБ + multipart-оверхед (UI шлёт файлы по одному).
    client_max_body_size 30M;

    # --- ССО-шлюз (по образцу correction-audio) ------------------------
    auth_request /_sso;

    # 401 → общий вход экосистемы с возвратом на поддомен.
    error_page 401 = @sso_login;

    # 403 НЕ перехватываем (§8.1): деактивированный аккаунт или неверный
    # секрет шлюза не лечатся повторным входом — явный 403 Forbidden.

    # Недоступность testing / ошибки внутреннего endpoint → 503.
    error_page 500 502 503 504 = @sso_unavailable;

    location = /_sso {
        internal;
        proxy_pass http://127.0.0.1:3000/api/internal/session;
        proxy_pass_request_body off;
        proxy_set_header Content-Length "";
        proxy_set_header Cookie $http_cookie;
        proxy_set_header X-Internal-Auth "<INTERNAL_AUTH_TOKEN>";
    }

    location @sso_login {
        return 302 https://bot-atelier.ru/login?next=https%3A%2F%2Ftranscribe.bot-atelier.ru%2F;
    }

    location @sso_unavailable {
        return 503;
    }

    # --- Приложение -----------------------------------------------------
    location / {
        proxy_pass http://127.0.0.1:8082;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_request_buffering off;
        proxy_read_timeout 900s;
    }
}
```

HTTPS-блок добавляет certbot (§9.6). Собственные 5xx приложения
проходят насквозь (`proxy_intercept_errors off`); ошибки соединения
(502/504) перехватываются в 503.

### 9.5. DNS

| Имя | Тип | Значение | TTL |
|-----|-----|----------|-----|
| `transcribe` | `A` | `2.26.112.123` | 3600 |

Явная A-запись добавляется **несмотря на wildcard `*`** — для
прозрачности и отладки. Проверка: `nslookup transcribe.bot-atelier.ru`.

### 9.6. TLS

```bash
certbot --nginx -d transcribe.bot-atelier.ru \
  --non-interactive --agree-tos --email admin@bot-atelier.ru
```

Сертификаты других поддоменов не затрагиваются.

### 9.7. `deploy/deploy.sh` (по образцу `deploy-mvp.sh`)

1. `docker compose up -d --build` (в `/opt/transcribe/deploy`);
2. ждать health-check `curl http://127.0.0.1:8082/api/health`
   (до 30 × 2 с);
3. `INTERNAL_AUTH_TOKEN` — из env или `/root/.internal_auth_token`;
4. `sed`-подстановка `<INTERNAL_AUTH_TOKEN>` →
   `/etc/nginx/sites-available/transcribe.bot-atelier.ru` + symlink в
   `sites-enabled`;
5. `nginx -t && systemctl reload nginx`.

### 9.8. `deploy/DEPLOY.md`

DNS (§9.5), создание `/opt/transcribe/.env`, выкат (§9.7), проверка
SSO-сценариев (без cookie → 302 на вход; с cookie → UI; `is_active=0`
→ 403; `testing` остановлен → 503 и новые, и открытые вкладки),
проверка «← На главную», проверка XLSX-формата (UUID не превращается в
экспоненту), rollback (§9.9).

### 9.9. Rollback

1. `docker compose down` (volume `transcribe-data` **оставить** —
   данные пользователей);
2. удалить symlink и файл `sites-available/transcribe.bot-atelier.ru`,
   `nginx -t && systemctl reload nginx`;
3. `git revert` каталога `transcribe/` и записи в `portal/subsystems.js`;
4. при полном выводе подсистемы по решению владельца — `docker volume rm
   transcribe-data` (данные пользователей будут потеряны);
5. TLS-сертификат можно оставить (не мешает).

13. SSO-сценарии: без `session_id` → 302 на общий вход с `next`;

15. `OPENAI_API_KEY` и `INTERNAL_AUTH_TOKEN` не попадают в git.
16. Запросы к OpenAI/Twin24 логируются без токенов, пароля и

17. Карточка подсистемы отображается на портале `bot-atelier.ru` и

## Приложение А. Базовый промпт разметки ролей (стадия 3)

> **Область применения:** используется на стадии 3 пайплайна (§2.3) с
> моделью `gpt-4o-mini`, `temperature=0`. Дословный текст системного
> промпта и few-shot-примеры — **вне скоупа v1** (уточняются и
> тестируются на 15–20 живых звонках заказчика перед продом; см. §10
> п.4). Ниже — **контракт промпта**, которому базовая версия должна
> соответствовать.

### А.1. Контракт системного промпта

**Роль модели:** разметчик телефонного диалога.

**Задача:** превратить сырой транскрипт (стадия 2) в построчную
разметку с ролями Оператор и Клиент.

**Признаки Оператора** (включить в системный промпт):
- здоровается первым, представляется компанией;
- задаёт уточняющие и направляющие вопросы;
- использует профессиональную лексику, скриптовые обороты («подскажите,
  пожалуйста», «позвольте уточнить»);
- управляет ходом разговора, переводит темы;
- прощается по скрипту («спасибо за звонок», «всего доброго»).

**Признаки Клиента:**
- описывает проблему / запрос от первого лица;
- задаёт вопросы о продукте/услуге/статусе;
- отвечает на вопросы оператора;
- эмоциональные реакции, паузы, спонтанная речь.

### А.2. Формат вывода (строгий)

- Строго построчно.
- Каждая строка начинается с одной из двух меток: `Оператор: ` или
  `Клиент: ` (с пробелом после двоеточия).
- Одна реплика = одна строка; многострочные реплики запрещены.
- Без нумерации, без таймкодов, без комментариев и мета-текста.
- Без пустых строк между репликами.

**Пример формата вывода (иллюстрация, не few-shot):**

```
Оператор: Здравствуйте, компания «Пример», меня зовут Анна. Чем могу помочь?
Клиент: Добрый день. Я вчера оформил заказ, но не получил подтверждение на почту.
Оператор: Подскажите, пожалуйста, номер заказа или телефон, на который оформляли.
Клиент: Телефон +7 900 000-00-00.
Оператор: Одну минуту, проверяю.
```

### А.3. Параметры вызова

- Модель: `gpt-4o-mini`.
- `temperature`: **0**.
- Таймаут попытки: 30 с.
- Первая попытка + до 3 повторов; паузы 2/4/6 с.
- Успех → `result_text` в БД; статус → `done`.
- Финальная неудача → `error` «разметка ролей не удалась после 3
  повторов: …».

### А.4. Дополнение few-shot (v1.1, вне скоупа v1)

После сбора 15–20 живых звонков заказчика:
- отобрать 3–5 репрезентативных примеров (короткий/длинный,
  спонтанная речь, перебивания, шум);
- встроить как few-shot примеры в системный промпт;
- протестировать на отложенной выборке;
- зафиксировать финальный текст промпта и набор few-shot в отдельном
  документе `.opencode/prompts/transcribe-roles.md` (создаётся в v1.1).
