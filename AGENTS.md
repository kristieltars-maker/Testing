# Экосистема «Тестирование ботов» — архитектурный каркас

Этот файл описывает общие (shared) сущности и правила, к которым должны
примыкать все подсистемы проекта, а также перечисляет существующие и
планируемые модули.

> **Роль файла:** единый источник истины для агентов при добавлении новых
> модулей. Если новая подсистема затрагивает ту же предметную область, что и
> существующая, изменения должны идти через общую абстракцию, а не через
> дублирование.

---

## 1. Общий каркас (Shared Kernel)

Все модули строятся поверх этих сущностей и механизмов.

### 1.1. Пользователи и аутентификация

- `users` — общая таблица пользователей.
  - Поля: `id`, `name`, `email`, `password_hash`, `role`, `is_active`,
    `created_at`.
  - Роли: `admin`, `tester`, `developer`, `manager`.
- `sessions` — серверные сессии в `httpOnly`-cookie.
- `middleware/auth.js` — проверка сессии и `requireRole(...)`.
- `AuthContext.jsx` / `api/client.js` — клиентская аутентификация.
- **Единый вход (SSO) для самостоятельных подсистем.** Общая сессия
  `session_id` отдаётся с атрибутом `Domain=.bot-atelier.ru`, поэтому
  валидна на всех поддоменах экосистемы. Подсистема `audio-correction`
  не заводит собственной сессии и не содержит кода аутентификации:
  nginx перед каждым запросом проверяет общую cookie через внутренний
  endpoint `testing` `GET /api/internal/session` (loopback +
  `X-Internal-Auth`) и пропускает запрос к MVP только при `200`, иначе
  редиректит на общий вход. Внутренний endpoint слушает только loopback
  и закрыт снаружи nginx `testing`. Детали — в
  `.opencode/architecture/audio-correction.md` (§3) и
  `.opencode/architecture/audio-correction-standalone.md`.

### 1.2. Проекты и участники

- `projects` — заказчик/проект.
  - Поля: `id`, `name`, `client_name`, `platform`, `slug`, `manager_id`,
    `created_by`, `created_at`.
- `bots` — бот внутри проекта (`project_id`, `name`, `description`).
- `project_members` — связь пользователя с проектом и ролью в нём
  (`tester`, `developer`, `manager`).

Правило: доступ к объектам модуля проверяется через членство в проекте
(админ, руководитель или участник). Новые модули должны повторять эту
модель.

> **Исключение — самостоятельные подсистемы.** Подсистема
> `audio-correction` вынесена в отдельное приложение на поддомене
> `correction-audio.bot-atelier.ru` и **не использует проекты** (`projects`,
> `bots`, `project_members`). Её связь с экосистемой ограничена входом
> (SSO, см. §1.1). Такое исключение допустимо только для подсистем,
> спроектированных как независимый эфемерный рабочий стол, и должно быть
> явно зафиксировано в архитектурном документе подсистемы.

### 1.3. Файлы и загрузки

- Файловое хранилище: `backend/src/uploads/{project_id}/`.
- Статика отдаётся по `/uploads/`.
- Загрузка через `multer`, имя файла формируется сервером
  (`{timestamp}-{random}{ext}`), оригинальное имя сохраняется в БД.

### 1.4. API и UI

- Backend: Express + SQLite (`sql.js`).
- Frontend: React + Vite + React Router.
- API клиент: `frontend/src/api/client.js`.
- Страницы модуля добавляются в `frontend/src/pages/` и регистрируются в
  `App.jsx`.
- Маршруты API модуля подключаются в `backend/src/server.js`.

## 2. Существующий модуль: testing (замечания)

**Цель:** трекинг замечаний тестировщика → скриптолога.

**Сущности:**

- `issues` — замечание внутри проекта (`local_number`, `status`, `bot_id`,
  `created_by`, `assigned_to`).
- `issue_messages` — лента сообщений внутри замечания.
- `issue_attachments` — скриншоты к сообщениям.

**Что уникально:**

- Статусная модель (`new`, `in_progress`, `clarification`, `waiting`,
  `done`, `cancelled`, `rejected`, `reopened`).
- Ролевые переходы статусов (тестировщик / скриптолог).
- Нумерация замечаний в рамках проекта.

## 3. Подсистема: audio-correction (корректор аудио-файлов)

> **Статус:** подсистема развёрнута на поддомене
> `correction-audio.bot-atelier.ru` как **исходный Acoustic Matcher MVP**
> (`web_app.py` + `static/index.html`, Python, обработка in-process) в
> контейнере `acoustic-matcher-mvp` (loopback `127.0.0.1:8081`). Доступ
> закрыт **SSO-шлюзом на nginx**: каждый запрос проверяется через
> внутренний endpoint `testing`. Кастомная реализация (Node-бэкенд,
> React-фронтенд, Python-sidecar, порты 3002/8080, PM2-процесс
> `audio-correction`) **выведена из эксплуатации**. Подсистема работает
> как **эфемерный рабочий стол**: своей БД и доменных таблиц нет,
> состояние живёт в памяти MVP, файлы — во временных каталогах, и всё
> теряется при рестарте контейнера.

**Цель:** дать аутентифицированному пользователю экосистемы один раз
загрузить эталонную аудиозапись и одну или несколько целевых записей,
запустить acoustic matching, получить скорректированные файлы, метрики и
отчёты, скачать результаты и уйти из подсистемы, после чего сервер
«забывает» всё, что было загружено и обработано.

**Границы модуля:**

- Исходники MVP: `audio-correction/mvp/` (`web_app.py`, `static/index.html`,
  `acoustic_matcher.py`, `requirements.txt`, `Dockerfile`,
  `docker-compose.yml`, `tests/`).
- Артефакты деплоя: `audio-correction/deploy/` (nginx-блок со SSO-шлюзом,
  compose/юнит MVP-контейнера, скрипт выката, `DEPLOY.md`).
- Не зависит от `testing` за пределами аутентификации: не использует
  `projects`, `bots`, `project_members`, `issues`, БД `testing`, его
  сервисы и страницы.
- Единственная связь — SSO (общая cookie `session_id` + внутренний
  endpoint `testing`; см. §1.1).

**Единый вход (SSO-шлюз nginx):**

- Общая cookie `session_id` с `Domain=.bot-atelier.ru` (ставит `testing`).
- nginx `correction-audio.bot-atelier.ru` на каждый запрос выполняет
  `auth_request` к `testing`: `GET /api/internal/session` по loopback
  (`127.0.0.1:3000`) с заголовком `X-Internal-Auth: <INTERNAL_AUTH_TOKEN>`.
- `200` → запрос проксируется к MVP (`127.0.0.1:8081`); `401` → redirect
  на `https://bot-atelier.ru/login?next=https%3A%2F%2Fcorrection-audio.bot-atelier.ru%2F`;
  `403` → `403 Forbidden` (неверный секрет или деактивированный аккаунт).
- Собственной сессии/аутентификационного кода у подсистемы нет.
- При недоступности `testing` не проходят и новые, и уже открытые вкладки
  (`503`): проверка выполняется на каждый запрос, а не один раз при входе.

**Модель данных (без проектов и БД):**

- **Нет доменных таблиц и нет собственной БД.** `recordings`,
  `audio_correction_tasks`, `match_versions`, `local_sessions`,
  `users_cache` не создаются.
- Состояние MVP — **in-memory** (`web_app.py`, словарь `SESSIONS`), ключ —
  собственный рабочий cookie MVP `acoustic_session` (32 hex; не связан с
  `session_id` и не является аутентификацией). При рестарте контейнера
  состояние теряется.
- Файлы (эталон, цели, результаты) — во временных каталогах ОС
  (`tempfile.mkdtemp`, префикс `acoustic_manager_`).
- **Очистка** естественная: рестарт контейнера/ОС; отдельного TTL/GC нет.

**UI и API (MVP, без изменений):**

- UI — исходный интерфейс MVP (`static/index.html`) с единственным
  добавленным анкером `← На главную` на `https://bot-atelier.ru/`.
- `GET /` — интерфейс; `GET /api/state` — состояние рабочего стола;
  `GET /audio?kind=reference|original|processed&id=…` — аудио/превью;
  `GET /api/export?ids=…` — ZIP со скорректированными WAV.
- `POST /api/reference` — эталон (multipart, поле `reference`);
  `POST /api/targets` — цели (multipart, поле `targets`);
  `POST /api/process` — обработка выбранных (`{ ids, settings }`).
- Обработка **синхронная, in-process** (`acoustic_matcher.process_one`),
  без sidecar и polling.

**Что переиспользует из общего каркаса:**

- `users`/`sessions` — только через SSO-шлюз (общая cookie + внутренний
  endpoint `testing`); собственной БД и сессии нет.
- Домен и TLS-конвенции (`/opt/<app>`, nginx-блок, certbot).

**Что уникально:**

- Самостоятельный деплой на поддомене, свой контейнер и nginx-блок;
  не входит в `testing`.
- Полностью эфемерная, без БД и доменной персистентности.
- Acoustic matching in-process (Python DSP), исходный UI MVP.
- Пакетный сценарий: 1 эталон + N целей → N скорректированных WAV.
- Прозрачный SSO-вход через nginx-шлюз (в самом MVP кода входа нет).

**Решённые продуктовые вопросы:**

1. **Роли и права.** Отдельная роль не нужна. Любой активный пользователь
   экосистемы, успешно прошедший SSO, может загружать аудио, запускать
   обработку и скачивать результаты. Проектной модели доступа нет.
2. **Связь с `issues`.** Связь с замечаниями не реализуется.
3. **Формат и обработка.** WAV, FLAC, MP3, M4A, AAC, OGG, Opus; результат —
   WAV PCM 16-bit, mono, с частотой дискретизации образца. Обработка
   синхронная, in-process; лимит загрузки задаёт MVP (`MAX_UPLOAD_BYTES`,
   500 МБ).
4. **Политика удаления.** MVP эфемерен: in-memory состояние и временные
   файлы; при рестарте контейнера всё теряется. Отдельного TTL/GC нет.
5. **Название модуля.** Slug — `audio-correction`, название —
   «Корректор аудио-файлов». Отдельный пункт меню в `testing` **не
   создаётся** (подсистема — отдельный сайт).

Подробности:
`.opencode/architecture/audio-correction.md` (SSO-шлюз, MVP, UI/API,
безопасность) и
`.opencode/architecture/audio-correction-standalone.md` (DNS, nginx/TLS,
MVP-контейнер, порты, env/секрет, выкат, вывод Node/React/sidecar из
эксплуатации, rollback).

## 4. Портал экосистемы: portal (`bot-atelier.ru`)

> **Статус:** новый общий (ecosystem-level) компонент. Публичная точка
> входа экосистемы, с которой пользователь выбирает подсистему.
> Добавляется **поверх** общего каркаса и не является подсистемой
> (`testing`/`audio-correction`).

**Цель:** дать пользователю одну публичную страницу на apex-домене
`bot-atelier.ru` со списком подсистем («Тестирование ботов», «Корректор
аудио-файлов») и ссылкой на общий вход, а также обеспечить возврат «На
главную» из каждой подсистемы **без выхода из аккаунта**.

**Границы компонента:**

- Отдельный статический сайт `portal/` в монорепозитории: `index.html`,
  `styles.css`, `subsystems.js`, `assets/`, референс `nginx.conf` и
  `DEPLOY.md`.
- **Без backend, без БД, без PM2-процесса, без Node.** Статику отдаёт
  nginx со своего домена.
- Не импортирует код подсистем. Единственная связь — ссылки и общий
  домен/SSO.
- Не читает и не меняет общую cookie `session_id`; не выполняет logout.

**Хостинг:**

- DNS (reg.ru): apex `@` → `2.26.112.123` (**сейчас указывает на
  `95.163.244.138` — требуется перенаправление**), `www` → тот же
  сервер.
- nginx-блок `/etc/nginx/sites-available/bot-atelier.ru`, один блок на
  `bot-atelier.ru` и `www.bot-atelier.ru`, root `/opt/portal`.
- **Страница входа живёт на apex**: `GET /login` отдаёт SPA-шелл сборки
  `testing` (`root /opt/testing-bots/frontend/dist`), `/assets/` и
  `/favicon.svg` — ассеты этой же сборки, `/api/` проксируется на
  `testing`-бэкенд (`127.0.0.1:3000`); `/api/internal/` закрыт.
  **Страница «Пользователи» тоже живёт на apex** — `GET /admin/users`
  отдаёт SPA-шелл той же сборки (пользователи принадлежат всем
  подсистемам экосистемы).
- Портальная иконка — `/portal-favicon.svg` (чтобы не пересекаться с
  favicon'ом login-страницы на `/favicon.svg`).
- TLS: `certbot --nginx -d bot-atelier.ru -d www.bot-atelier.ru`.
- Сосуществование: портал не пересекается с
  `testing.bot-atelier.ru` и `correction-audio.bot-atelier.ru` по портам,
  процессам и путям; сертификаты поддоменов не затрагиваются.

**Аутентификация (публичная, без backend):**

- Портал публичен и не имеет собственной сессии/login/logout.
- Действие «Войти» — ссылка на общий вход экосистемы с возвратом на
  портал: `https://bot-atelier.ru/login?next=https%3A%2F%2Fbot-atelier.ru%2F`
  (whitelist `next` в `testing` уже допускает apex `bot-atelier.ru`).
- Переход по карточке подсистемы запускает SSO внутри подсистемы
  (`testing` — `/api/me`; `correction-audio` — SSO-шлюз nginx на
  `auth_request` к `testing`, локальной сессии подсистемы нет). Если
  пользователь не вошёл, подсистема/шлюз уводит на общий вход.
- **Имя пользователя на портале не показывается:** общая cookie
  `HttpOnly` и клиентским JS не читается. Показ имени потребовал бы
  отдельного backend (вне текущей архитектуры).
- Секретов на портале нет; `/api/internal/*` не вызываются.

**«На главную» из подсистем (без выхода):**

- Общий приём: plain-анкер `<a href="https://bot-atelier.ru/">На главную</a>`
  (переход кросс-доменный, не React Router `<Link>`). Никаких вызовов
  `logout()` / `POST /auth/logout` / `DELETE /session`.
- `testing`: ссылка в компоненте `Layout` — `frontend/src/App.jsx`
  (навигационная панель).
- `correction-audio`: ссылка `← На главную` в шапке исходного интерфейса
  MVP — `audio-correction/mvp/static/index.html`.
- Константа `PORTAL_URL = 'https://bot-atelier.ru/'` — в локальном
  `constants/ecosystem.js` `testing` (дублирование осознанно, как и у
  других общих утилит при независимом деплое); в MVP ссылка задана
  литералом.
- Общая cookie `session_id` (`Domain=.bot-atelier.ru`) сохраняется;
  рабочая сессия MVP (`acoustic_session`) и временные файлы при переходе
  не удаляются.

**Что переиспользует из общего каркаса:**

- Домен и TLS-конвенции (`/opt/<app>`, nginx-блок, certbot).
- Общий вход (SSO) — **только ссылкой** на `testing/login`; сам портал в
  механизме SSO не участвует.
- Общую навигационную конвенцию «На главную».

**Что уникально:**

- Единственный компонент экосистемы **без backend**.
- Единственный на apex-домене; объединяет подсистемы навигационно.
- Каталог подсистем в `portal/subsystems.js` (расширение = одна запись).

**Решённые продуктовые вопросы:**

1. **Форма.** Статический сайт без сборки и фреймворка (низкая
   поддержка; SPA/backend избыточны). Подробности — §2 документа.
2. **Backend.** Не нужен. При необходимости показывать имя — добавляется
   позже отдельным сервисом.
3. **Аутентификация.** Публичный портал; «Войти» — ссылка на общий вход
   с `next` на портал; собственного logout нет.
4. **Список подсистем.** `testing` и `correction-audio`; расширяется
   записью в `portal/subsystems.js`.
5. **«На главную».** Plain-анкер на `https://bot-atelier.ru/` в шапке
   каждой подсистемы; сессия не завершается.

Подробности: `.opencode/architecture/portal.md` (форма, структура
репозитория, DNS/nginx/TLS, аутентификация, «На главную», риски).
