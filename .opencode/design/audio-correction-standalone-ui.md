> **Статус:** актуальный UI-дизайн для самостоятельного приложения на
> поддомене `correction-audio.bot-atelier.ru`.
> **Заменяет:** `.opencode/design/audio-correction-ui.md` (версия внутри
> `testing`, привязанная к проекту) — оставлен как исторический.
> **Связанные документы:**

## 2. Карта маршрутов и состояний приложения

| Маршрут | Доступ | Назначение |
|---|---|---|
| `/login` | публичный | Посадочная страница с кнопкой «Войти через экосистему». |
| `/` | защищённый | Единый эфемерный рабочий стол. |
| `*` | — | Редирект на `/`. |

Приложение — **SPA с одной содержательной страницей**. Внутренней навигации
между разделами нет: всё живёт на `/` секциями. Поэтому «навигационные
guards» в основном ловят уходы из приложения (browser back/forward, logout,
перезагрузка), а не переходы между экранами.

Состояния приложения на уровне route `/`:

```
Загрузка → /api/me
   ├── 200 + user ───────────────► Workspace (empty | с файлами | processing | results)
   ├── 401 нет локальной и общей cookie ──► redirect /login
   ├── 403 аккаунт деактивирован ─────────► AuthError («Аккаунт отключён»)
   └── 503 сервис входа недоступен ───────► AuthUnavailable («Вход временно недоступен»)
```

## 3. Вход и аутентификация (entry / auth states)

### 3.1. Посадочная страница `/login` (минимальный landing)

Используется, когда пользователь не аутентифицирован. Отдельной формы
email/пароля **нет** — пароль вводится только на стороне `testing`.

```
┌──────────────────────────────────────────────────────┐
│  ♪  Корректор аудио-файлов                            │  ← простая шапка, без пользователя
├──────────────────────────────────────────────────────┤
│                                                      │
│        ┌────────────────────────────────────────┐    │
│        │  Корректор аудио-файлов                 │    │
│        │                                        │    │
│        │  Разовое акустическое выравнивание      │    │
│        │  записей по эталону.                    │    │
│        │                                        │    │
│        │  Файлы и результаты не сохраняются:     │    │
│        │  они живут только во время визита и     │    │
│        │  удаляются при закрытии.                │    │
│        │                                        │    │
│        │  [  Войти через экосистему  ]           │    │
│        │                                        │    │
│        │  Нет доступа? Обратитесь к админу       │    │
│        │  экосистемы.                            │    │
│        └────────────────────────────────────────┘    │
│                                                      │
└──────────────────────────────────────────────────────┘
```

- **Назначение:** объяснить эфемерность и увести на общий вход.
- **Кнопка «Войти через экосистему»** — primary, ведёт на
  `https://testing.bot-atelier.ru/login?next=https://correction-audio.bot-atelier.ru/`.
  Это обычный `<a href>` (полная навигация), не SPA-переход.
- **Роли:** страница доступна всем.
- **Переиспользование:** та же типографика и `.card`-паттерн, что в
  `testing`. Отдельный дизайн не изобретается.
- **Edge case:** если `next` на стороне `testing` не прошёл валидацию
  whitelist, пользователь вернётся на `/` общего приложения — это
  ответственность `testing`, а не standalone.

### 3.2. Загрузка сессии (bootstrap) при открытии `/`

- Пока `GET /api/me` не ответил — полноэкранный плейсхолдер `.empty`
  «Загрузка…» (как в `ProtectedRoute`). Пользователю не показывается ни
  рабочее место, ни landing, пока не ясен auth-статус.
- Если есть общая cookie `session_id`, но нет локальной `ac_session_id` —
  backend прозрачно делает bootstrap (§3.3 архитектуры). UI видит просто
  успешный `/api/me`; отдельного экрана «входим» не требуется.
- Если bootstrap не удался по сети/timeout — тот же экран загрузки уходит
  в состояние ошибки (§3.4).

### 3.3. Вошедший пользователь — Workspace

- `/api/me` → `{ user }`. Показывается app shell (§4) и рабочий стол (§5).
- В шапке — имя и роль пользователя. Роль **не влияет на права**: любой
  активный пользователь экосистемы имеет полный доступ. Ролевых disabled-
  состояний внутри модуля нет.
- Если workspace пуст → пустое состояние рабочего стола (§5.1).
- Если в workspace есть данные (файлы/настройки/run) → восстанавливается
  из `GET /api/session`.

### 3.4. Сессия истекла / утеряна

Локальная сессия истекла, уничтожена logout'ом, workspace удалён по TTL
или очищен при старте сервера. Возможны два подслучая:

**A. Общая cookie ещё валидна** — bootstrap проходит прозрачно, пользователь
просто возвращается на пустой рабочий стол. Спец-экран не нужен.

**B. Общая cookie тоже истекла** — `GET /api/me` → `401`, редирект на
`/login` (landing).

**C. Сессия «пропала» во время работы** (404/410 от `/api/session` или
polling). Показывается статус lost (как в текущей реализации
`markSessionLost`):

```
┌──────────────────────────────────────────────────────┐
│  ♪  Корректор аудио-файлов      Иван · tester  [Выйти]│
├──────────────────────────────────────────────────────┤
│                                                      │
│   ┌──────────────────────────────────────────────┐   │
│   │  Сессия устарела или была закрыта.           │   │
│   │  Все файлы и результаты удалены.             │   │
│   │                                              │   │
│   │           [ Обновить страницу ]              │   │
│   └──────────────────────────────────────────────┘   │
│                                                      │
└──────────────────────────────────────────────────────┘
```

- Текст: «Сессия устарела или была закрыта в другой вкладке. Все файлы и
  результаты удалены.» (сохраняем существующую формулировку).
- Кнопка «Обновить страницу» → `window.location.reload()` → новый bootstrap
  (при валидной общей cookie создаётся новый пустой workspace).
- Кнопка **«Выйти»** в шапке остаётся доступной.

### 3.5. Сервис входа экосистемы недоступен (`503`)

`POST /api/auth/session` вернул `503 { error: 'Сервис входа временно
недоступен' }`. Это состояние **только для входа**: уже вошедшие локальные
сессии продолжают работать.

```
┌──────────────────────────────────────────────────────┐
│  ♪  Корректор аудио-файлов                            │
├──────────────────────────────────────────────────────┤
│                                                      │
│   ┌──────────────────────────────────────────────┐   │
│   │  Вход временно недоступен                    │   │
│   │                                              │   │
│   │  Сервис аутентификации экосистемы не         │   │
│   │  отвечает. Попробуйте ещё раз через          │   │
│   │  несколько минут.                            │   │
│   │                                              │   │
│   │     [ Повторить вход ]   [ На главную ]      │   │
│   └──────────────────────────────────────────────┘   │
│                                                      │
└──────────────────────────────────────────────────────┘
```

- **«Повторить вход»** — повторный `POST /api/auth/session` + `GET /api/me`,
  кнопка на время запроса в состоянии «Проверяем…».
- **«На главную»** — переход на `/login` (landing).
- Это ошибка входа, а не ошибка обработки: рабочий стол не отрисовывается.
- Edge case: если 503 прилетел посреди работы (маловероятно, т.к. runtime-
  зависимость от `testing` отсутствует) — показывается **неблокирующий
  баннер** сверху рабочего стола «Сервис входа недоступен. Текущая работа
  продолжится.»; рабочее место не разрушается.

### 3.6. Аккаунт деактивирован (`403`)

Внутренний endpoint вернул `403 Account deactivated`. Экран входа:

- Заголовок «Доступ отключён».
- Текст «Ваш аккаунт деактивирован. Обратитесь к администратору
  экосистемы.»
- Кнопка **«Выйти»** (очищает локальную сессию, ведёт на `/login`).
- Никаких кнопок повторного входа: бессмысленно до реактивации.

### 3.7. Матрица auth-состояний

| Состояние | Триггер | Что показываем | Действие пользователя |
|---|---|---|---|
| Загрузка | `/api/me` в полёте | `.empty` «Загрузка…» | — |
| Не аутентифицирован | 401, нет cookie | `/login` landing | «Войти через экосистему» |
| Аутентифицирован | 200 | Workspace | работа |
| Сессия истекла «тихо» | 401 после валидной общей cookie | новый пустой Workspace | работа |
| Сессия утеряна в работе | 404/410 | `.empty` lost | «Обновить страницу» |
| Сервис входа недоступен | 503 на bootstrap | отдельный экран | «Повторить вход» |
| Аккаунт деактивирован | 403 | отдельный экран | «Выйти» |

## 4. App shell (верхняя панель)

Единая шапка приложения, видимая на `/` (на `/login` — упрощённая версия
без пользователя, см. §3.1).

```
┌────────────────────────────────────────────────────────────────────────────┐
│  ♪  Корректор аудио-файлов          Иван Иванов · Тестировщик  [Выйти]  [Закрыть / Забыть] │
└────────────────────────────────────────────────────────────────────────────┘
```

### 4.1. Состав и поведение

| Элемент | Описание | Состояния |
|---|---|---|
| **Название** «Корректор аудио-файлов» | Слева, жирным, кликабельно (ведёт на `/`). | Всегда доступно. |
| **Индикатор пользователя** | `{user.name} · {ROLE_LABELS[user.role]}` (маппинг ролей — как в экосистеме). | Виден только аутентифицированному. При загрузке — скрыт/плейсхолдер. |
| **«Выйти»** | Вторичная кнопка. См. поведение в §4.2. | Если есть данные — открывает модалку подтверждения; иначе выходит сразу. |
| **«Закрыть / Забыть»** | Опасная вторичная кнопка (красный контур/текст), `.btn-danger-outline`. | **Disabled**, если workspace пуст (нечего забывать) — с `title` «Нет данных для удаления». **Enabled**, если есть эталон/цели/run. |

**Ключевое изменение:** в прежнем дизайне «Закрыть / Забыть» стояла в
заголовке страницы (шапка проекта). Здесь она переезжает в **app shell
top bar**, потому что шапки проекта больше нет. Рабочий стол начинается
сразу с секций.

### 4.2. Взаимодействие «Выйти» и «Закрыть / Забыть»

- **«Закрыть / Забыть»** — только очистка workspace и файлов, пользователь
  остаётся в подсистеме. После `DELETE /api/session` возвращаемся на пустой
  рабочий стол того же пользователя (`/`). Это сценарий «закончил работу,
  начать заново / уйти с чистой страницей».
- **«Выйти»** — уничтожение локальной сессии (`POST /api/auth/logout`) и
  переход на `/login`.
  - Если данных нет — выполняется сразу.
  - Если данные есть — открывается модальное подтверждение (см. §7.3,
    заголовок «Выйти и забыть данные?»), потому что logout уничтожает и
    workspace (`deleteOnSessionDestroyed`). После подтверждения:
    `DELETE /api/session` → `POST /api/auth/logout` → `/login`.
- Обе кнопки в шапке; порядок: «Выйти» левее, «Закрыть / Забыть» правее
  (опасное действие — последним, как в существующих модалках).
- **Проектной навигации в шапке нет.** Никаких вкладок, ссылок «Проекты»,
  «Замечания», «Управление».

## 5. Единый рабочий стол «Корректор аудио-файлов»

### 5.1. Назначение и роли

Экран используется любым активным пользователем экосистемы, прошедшим SSO.
Пользователь загружает эталон, цели, настраивает параметры, запускает
асинхронную обработку, слушает и скачивает результаты, после чего закрывает
workspace. Ролевых ограничений нет.

### 5.3. Секция [1] «Эталонная запись» (без изменений логики)

- Карточка `.audio-section` с заголовком `[1] Эталонная запись`.
- Зона `audio-dropzone` (один файл): иконка `♪`, подсказка
  «Перетащите эталонный аудиофайл или нажмите для выбора», строка форматов
  и лимита.
- После загрузки — `audio-file-card`: имя, размер · кГц · каналы ·
  длительность, кнопка удаления (корзина), `<audio>`-плеер.
- Загрузка сразу после выбора; затем автоматически
  `POST /session/reference/analyze` (профиль + рекомендации).
- Ошибки формата/размера — красная плашка `.audio-error` под зоной.

### 5.4. Секция [2] «Целевые записи» (без изменений логики)

- Заголовок `[2] Целевые записи`, зона drag-and-drop с `multiple`.
- Список `audio-file-list`: номер, имя, размер · кГц · длительность,
  бейдж «Готово», мини-плеер, кнопка удаления.
- Ошибки валидации — один блок `.audio-error` со строками
  `<strong>имя</strong>: причина`. Валидные файлы всё равно загружаются.
- Запрещено добавлять больше 50 целей (серверный лимит) — при превышении
  показывается ошибка, лишние не добавляются.

### 5.5. Секция [3] «Настройки обработки» (без изменений)

**Макро-ручки** (2 шт., `.macro-row` + слайдеры с тремя метками):
- «Дистанция микрофона»: Близко / Средне / Далеко.
- «Реверберация / эхо»: Сухо / Средне / Реверберированно.
- Кнопка «Сбросить макро».
- Параметры, изменённые макро, помечаются точкой `macro-dot`.

**Рекомендации Sidecar:**
- Строка анализа «Анализ эталона…» (спиннер), пока идёт `/analyze`.
- Список рекомендаций + кнопка «Применить рекомендации».
- Если рекомендаций нет: «Автоматических рекомендаций нет»; если эталон не
  загружен: «Загрузите эталонную запись, чтобы получить рекомендации.»

**Продвинутые параметры (18, 6 групп):**
- Уровни и громкость (2), Спектр и тембр (5), Динамика (1),
  Пространство / реверберация (6), Лимитирование (1), Прочее (3).
- Группы сворачиваемые; по умолчанию открыта только «Уровни и громкость».
- Каждый параметр: подпись, единица, ползунок + числовое поле, hint.
- Источник списка — `PARAM_GROUPS` в `constants/audioCorrection.js`
  (уже 18 параметров; расхождений с макетом нет).
- **Дизейбл при обработке:** все поля настроек `disabled`, пока
  `run.status === 'running'`.

### 5.6. Запуск обработки

- Кнопка `[ Запустить обработку ]` под настройками (`.start-row`).
- **Enabled:** есть эталон, ≥1 цель, нет активной обработки, нет
  незавершённого запроса.
- **Disabled:** иначе; рядом серый хинт «Загрузите эталонную запись» или
  «Добавьте хотя бы одну целевую запись».
- Во время обработки текст «Запуск…», кнопка disabled.
- Повторный запуск с теми же файлами и новыми настройками возможен:
  предыдущий `run` перезаписывается, старые `outputs/` удаляются.

### 5.7. Секция [4] «Результаты текущего запуска»

- Появляется, когда есть `run` и он не в статусе `running` (иначе вместо
  неё — `.processing-status`, см. §6.3).
- Бейдж общего статуса run: Успешно / Частичный успех / Ошибка / Отменено.
- Плеер «Эталон» в начале секции (одна запись).
- По каждой цели — `.card.result-card`: имя, бейдж статуса
  (в очереди / обрабатывается / успешно / ошибка / отменено),
  waveform-placeholder, два плеера «Исходник» / «Исправленный», метрики
  (LUFS, True Peak, LRA, SNR, Spectral Distance; `—` для отсутствующих),
  кнопки «Скачать исправленный» / «Скачать отчёт».
- Футер: «Скачать все результаты (ZIP)» (disabled без успешных), «Скачать
  полный отчёт».
- Плееры независимы (не останавливают друг друга) — сохраняем прежнее
  поведение для сравнения.

## 6. Состояния экрана

### 6.1. Пустой workspace (empty)

- Секции [1] и [2] показывают зоны drag-and-drop с иконкой и подсказкой.
- Секция [3] доступна, но рекомендации — «Загрузите эталонную запись…».
- Кнопка «Запустить обработку» disabled + хинт.
- Секция [4] и `.processing-status` скрыты.
- «Закрыть / Забыть» disabled (нечего удалять).

### 6.2. Загрузка файлов

- В зоне/списке — строка со спиннером «Загрузка…»; зона временно disabled.
- На время `busyAction` соответствующая секция недоступна для новых
  действий.
- После успеха список/карточка обновляются без перезагрузки страницы.

### 6.3. Обработка (processing)

```
┌──────────────────────────────────────────────────────────────┐
│  [Обработка]  ⏳  Обработка выполняется…        [⏹ Отменить]  │
│  [██████████████░░░░░░░░░░░░░░░░░░░░]  (indeterminate/fill)  │
│                                                              │
│  target_1.wav                           [Обрабатывается]     │
│  target_2.wav                           [В очереди]          │
│  target_3.wav                           [Успешно]            │
└──────────────────────────────────────────────────────────────┘
```

- Блок `.processing-status` появляется сразу после `POST /session/process`.
- Спиннер + бейдж статуса, кнопка «⏹ Отменить» (при нажатии «Отмена…»).
- Прогресс: indeterminate при `running` (sidecar не даёт точных долей) либо
  `processed / total` по завершённым целям.
- Все секции ввода/настроек `disabled`.
- Polling `GET /session/runs/:runId` каждые 2 секунды.
- **Polling-ошибка** — не рушит экран: сверху неблокирующий баннер
  `.audio-warning` «Не удалось обновить статус» + «Повторить».

### 6.4. Частичный успех

- Общий бейдж run «Частичный успех».
- Успешные цели: полные карточки с плеерами и метриками, скачивание
  доступно.
- Failed-цели: карточка с бейджем «Ошибка», текстом `entry.error`,
  скачивание disabled, кнопок «Повторить» по отдельной цели нет
  (перезапуск общий — кнопка «Запустить обработку»).
- ZIP и полный отчёт доступны, если есть ≥1 успешный результат.

### 6.5. Полная ошибка

- Бейдж «Ошибка», плашка `.audio-error` с текстом из sidecar и кнопка
  «Повторить запуск».
- Ошибки `504/503/502` от sidecar (таймаут/недоступен/ошибка) выводятся тем
  же паттерном; формулировка берётся из ответа сервера.

### 6.6. Отмена

- Пользователь нажал «Отменить» → run `cancelled`.
- Показываются только успевшие обработаться цели; остальные — «Отменено».
- Секция результатов отрисовывается по общим правилам.

### 6.7. Сессия утеряна

- См. §3.4C: `.empty` с текстом об утере и кнопкой «Обновить страницу».

## 7. Guards: защита от случайного ухода

В standalone внутренней навигации почти нет, поэтому guards сводятся к
трём механизмам. Все они активны только когда в workspace **есть данные**
(`hasData && !closing`) — как в текущей реализации.

### 7.1. `beforeunload` (закрытие вкладки / перезагрузка)

- При наличии данных (`эталон || targets.length || run`) вешается
  `beforeunload` со стандартным браузерным предупреждением.
- `event.returnValue = ''`; кастомный текст браузер игнорирует (показывает
  свой).
- Снимается, когда данных нет.

### 7.2. Навигационный guard (browser back/forward, внутренние ссылки)

- `useNavigationGuard({ active: hasData && !closing })` переносится как есть.
- **Что перехватывает в standalone:**
  - нажатие «назад»/«вперёд» браузера (`popstate`) → возврат и показ модалки
    подтверждения;
  - любые same-origin `<a href>` (например, ссылка на `/login`, если
    появится) → перехват и подтверждение.
- **Что НЕ перехватывает:** клики по «Выйти» и «Закрыть / Забыть» — это
  кнопки, а не ссылки; они обрабатываются явно (§4.2).
- При подтверждении: `DELETE /api/session` → `guard.confirm()` → уход.
  При отмене пользователь остаётся на рабочем столе.
- Заголовок модалки при уходе: «Покинуть корректор и забыть данные?».

### 7.3. Явная модалка «Закрыть / Забыть»

Переиспользуется `CloseConfirmModal`:

```
┌──────────────────────────────────────────────┐
│ Закрыть корректор и забыть данные?           │
│                                              │
│ Все загруженные файлы, результаты            │
│ обработки и отчёты будут безвозвратно        │
│ удалены. Это действие нельзя отменить.       │
│                                              │
│              [Отмена]  [Закрыть / Забыть]    │
└──────────────────────────────────────────────┘
```

- Открывается из top bar по «Закрыть / Забыть».
- Если run активен, confirm-кнопка: «Остановить и забыть» (отменяет sidecar-
  задачу перед очисткой). Формулировка уже есть в `CloseConfirmModal`.
- Во время подтверждения — «Удаление…», кнопки disabled.
- Для выхода из аккаунта используется та же модалка с заголовком
  «Выйти и забыть данные?» и confirm «Выйти и забыть»; после очистки —
  `POST /api/auth/logout` и переход на `/login`.
- Закрытие по Escape/клику по оверлею — только когда действие не выполняется.

### 7.4. Вторая вкладка

- Архитектура (§4.2) определяет workspace по локальной сессии; две вкладки
  одного браузера делят cookie, значит **делят workspace** («последняя
  активная выигрывает»). Это осознанное поведение.
- Прежний `detectTabConflict` был привязан к `projectId`; в standalone
  `projectId` нет. Варианты (требуют решения, §8):
  - **A (рекомендуется):** сохранить UI-предупреждение «Корректор уже
    открыт в другой вкладке. Изменения в этой вкладке могут
    конфликтовать.» + «Продолжить здесь», но без ключа проекта (константа
    на origin).
  - **B:** убрать конфликт-баннер совсем, положившись на серверную
    семантику.

## 8. Адаптивность

| Ширина | Поведение |
|---|---|
| **≥ 1024 px** | Полный макет: `.page` центрирован, топ-бар в одну строку, настройки и результаты в карточках. |
| **768–1024 px** | Настройки и результаты — в одну колонку; топ-бар может перенести строку. |
| **< 768 px** | Топ-бар в две строки: (1) название + пользователь, (2) «Выйти» и «Закрыть / Забыть» — кнопки по ширине, «Закрыть / Забыть» доступна всегда. Волновые формы (`.waveform`) скрываются, остаются плееры и метрики. Кнопки действий в карточке результата — вертикально. Таблица метрик перестраивается в 2 колонки. |
| **< 480 px** | Хинты-подсказки и второстепенный текст укорачиваются; имя пользователя может сокращаться до имени без роли. |
| **Touch** | Ползунки макро/параметров увеличиваются по высоте для захвата пальцем; зоны drag-and-drop работают как `input[type=file]` по нажатию. |

Особенности standalone по сравнению с прежней версией: убираются правила
`.project-tabs`/`.project-tab`; медиа-правила для них не переносятся.

## 9. Переиспользование и согласование с экосистемой

- **Контейнер и типографика:** `.page` (max-width 1100, padding 24/20/60),
  `.page-header`, `.title`, `.muted` — как в `testing`.
- **Карточки:** `.card`, `.audio-section`, `.result-card`.
- **Бейджи статусов:** цвета и подписи из `constants/audioCorrection.js`
  (`RUN_STATUS_*`, `TARGET_STATUS_*`).
- **Кнопки:** primary (голубая), `.btn-secondary`, `.btn-danger`,
  `.btn-danger-outline`, `.btn-sm`, `.icon-btn` — из `index.css`.
- **Пустые состояния:** `.empty`.
- **Модалки:** `.modal-overlay`, `.modal`, `.modal-header`, `.modal-actions`.
- **Плееры:** нативные `<audio className="audio-player">`.
- **Notion о standalone-специфике:** в `testing` нет доступа к `testing`-
  `AuthContext` (форма логина), поэтому `AuthContext` standalone работает
  только с `/api/me` + `logout` + редиректом на общий вход. Визуально шапка
  повторяет навигацию `testing` (название слева, пользователь и «Выход»
  справа), но без ссылок-разделов.

## 10. Открытые вопросы (требуют уточнения)

1. **Поведение «Выйти» при наличии данных.** В §4.2 предложено просить
   подтверждение («Выйти и забыть данные?»). Подтвердить, что logout
   действительно должен удалять workspace, либо logout не должен трогать
   workspace (тогда logout просто завершает локальную сессию, а данные
   убирает GC по TTL).
2. **Вторая вкладка.** Оставляем UI-предупреждение (§7.4 вариант A) или
   полагаемся только на сервер (§7.4 вариант B)?
3. **Формат отчёта.** От чего зависят кнопки: единый `report.json` или
   возможен PDF/HTML из sidecar? Сейчас — фиксированные JSON-действия.
4. **TTL-подсказка.** Нужно ли показывать на рабочем столе живой обратный
   отсчёт до TTL (1 час), или достаточно статичной строки-предупреждения?
5. **Показ ошибки 503 во время работы.** Если принять гипотезу, что runtime-
   зависимость от `testing` отсутствует, спец-баннер §3.5 не нужен. Если
   периодическая ре-валидация будет включена — баннер нужен.
6. **Точные подписи и диапазоны параметров** (уже сведены в
   `constants/audioCorrection.js`, но финальное согласование с владельцем
   sidecar остаётся).
7. **Брендинг landing.** Использовать ли логотип/цвета экосистемы или
   минимальную иконку `♪`?
