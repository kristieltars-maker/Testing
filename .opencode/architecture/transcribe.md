# Архитектура подсистемы `transcribe` (транскрибация звонков, этап ТЗ)

> **Статус:** этап подготовки ТЗ, **до реализации**. Кода подсистемы в
> репозитории нет. Спроектирована как **самостоятельная (standalone)
> подсистема** по образцу `audio-correction`: поддомен
> `transcribe.bot-atelier.ru`, один Docker-контейнер `transcribe-app` за
> nginx SSO-шлюзом, **лёгкая персистентность** (SQLite + файлы в
> docker-volume, TTL 24 ч), токены Twin24 — только в памяти.
>
> **Язык документа:** русский.
> **Назначение:** границы и обоснование решений, топология, SSO-шлюз,
> модель данных и состояния, UI/API, безопасность, выкат, риски, открытые
> вопросы, черновик секции AGENTS.md.
> **Связанные документы:** `AGENTS.md` (§1 общий каркас, §1.2 правило
> исключения из проектной модели, §4 портал),
> `.opencode/architecture/audio-correction.md` (SSO-шлюз, прецедент
> standalone), `.opencode/architecture/audio-correction-standalone.md`
> (DNS/nginx/TLS, выкат), `.opencode/architecture/portal.md` (каталог
> подсистем).
>
> **Только архитектура.** Кода здесь нет; nginx/compose-фрагменты —
> ориентир для выката, как в связанных документах.

## 1. Резюме решений

| Вопрос | Решение |
|--------|---------|
| **Классификация** | Самостоятельная подсистема на поддомене `transcribe.bot-atelier.ru` по образцу `audio-correction`, **не** модуль `testing`. Проектной модели нет (`projects`/`bots`/`project_members`/`issues` не используются). |
| **Название** | Slug `transcribe`, название «Транскрибация звонков», поддомен `transcribe.bot-atelier.ru`, контейнер `transcribe-app`, volume `transcribe-data`, cookie `transcribe_ws`, серверный каталог `/opt/transcribe`. Альтернатива `call-transcription` («Расшифровка звонков») отклонена: длиннее, преимуществ нет. |
| **Персистентность** | **Лёгкая (вариант b):** состояние задач и результаты — SQLite в docker-volume + TTL-GC; WAV — в том же volume; токены Twin24 — **только в RAM**. Полностью эфемерная модель (a) отклонена (§4.1). |
| **Рантайм** | **Один Python-контейнер** (`transcribe-app`, FastAPI + uvicorn) с **in-process асинхронной очередью** (asyncio, пул 3–5). Redis/Celery не вводится (Redis в экосистеме нет, приоритет — минимальная операционная сложность); Node + Python-sidecar отвергнут (прецедент выведен из эксплуатации). |
| **Порты/процессы** | Loopback `127.0.0.1:8082` → контейнер `:8080`; `restart: unless-stopped`; без PM2. |
| **SSO** | nginx `auth_request` к `testing: GET /api/internal/session` дословно по образцу `correction-audio`; локальной сессии подсистемы нет. **403 — явный `403 Forbidden`, без редиректа** (§3.3). |
| **Доступ** | Все активные пользователи экосистемы, все роли; проектной модели нет (ТЗ №6). Идентичность внутри подсистемы неизвестна — как у `correction-audio`. |
| **Статусы** | `queued` → `transcribing` → `labeling` → `done`/`error` («в очереди» / «транскрибируется» / «размечаются роли» / «готово» / «ошибка»). Скачивание из Twin24 — подшаг стадии «транскрибируется». |
| **OpenAI-пайплайн** | `gpt-4o-transcribe` (таймаут 30 с на попытку, ≤3 повторов, паузы 2/4/6 с) → `gpt-4o-mini` разметка ролей Оператор/Клиент (`temperature=0`, те же повторы). Параллелизм 3–5 (env `TRANSCRIBE_WORKERS`, по умолчанию 4, клампится в [3, 5]). |
| **Twin24** | Пароль не хранится и не логируется (один запрос логина); `token`/`refreshToken` — в памяти процесса, ключ — workspace; ttl = 86400; авто-refresh проактивно и по 401. Импорт: смешанные строки UUID/ссылок построчно, ошибки по строкам без блокировки валидных. |
| **Результат** | XLSX (openpyxl), две колонки: «ID диалога» (принудительно текстовый формат ячейки) и «Текст транскрибации» (размеченный текст или текст ошибки). Кнопка «Скачать результат (Excel)» — когда **все** файлы терминальны; частичные ошибки не блокируют. |
| **Лимиты (предложение)** | 25 МБ на файл (жёсткий лимит API OpenAI), ≤50 файлов на workspace, ≤1 ГБ аудио на workspace, nginx `client_max_body_size 30M` (UI шлёт файлы по одному), TTL 24 ч (§10, вопрос 3). |
| **Очистка** | После **первой успешной выдачи** XLSX: WAV и промежуточные сырые транскрипты удаляются сразу (итоговые тексты — до TTL, повторное скачивание возможно). TTL-GC каждые 10 мин. |
| **Портал** | Одна запись в `portal/subsystems.js` (id `transcribe`, иконка «микрофон», §8.1) + синхронизация AGENTS.md §4 при обновлении. |
| **«На главную»** | Plain-анкер `← На главную` в шапке `static/index.html`; без logout (§6). |

## 2. Границы, топология, структура репозитория

### 2.1. Классификация: почему standalone, а не модуль `testing`

| Критерий | Модуль внутри `testing` | Standalone-подсистема (выбрано) |
|----------|-------------------------|--------------------------------|
| Проектная модель | Требует `projects`/`project_members` | Не нужна (ТЗ №6) — совпадает с исключением §1.2 AGENTS.md |
| Рантайм | Express + SQLite, синхронные запросы | Нужны Python (openai, openpyxl), asyncio-очередь, внешние вызовы Twin24/OpenAI |
| Сценарий | Живёт в UI трекинга замечаний | Пакетный сценарий «загрузил → обработал → скачал XLSX → ушёл» |
| Связь с `issues` | Подразумевалась бы | Не реализуется (как у `audio-correction`) |
| Выкат | Вместе с `testing` (PM2, apex-сборка) | Отдельный контейнер/поддомен, независимые релизы и риски |

Подсистема не разделяет с `testing` ни одной доменной сущности — общих
абстракций на уровень экосистемы не выносится (пересечения с «замечаниями»
нет, дублирования доменной логики нет).

**Относительно правила §1.2 AGENTS.md** («исключение допустимо только для
независимого эфемерного рабочего стола»): `transcribe` — самодостаточный
рабочий стол **с ограниченным временем жизни** (TTL 24 ч, удаление после
выдачи результата, без межмодульных данных). Отклонение от буквы
«эфемерный» (лёгкая персистентность в рамках TTL) фиксируется этим
документом, как того требует правило; при обновлении AGENTS.md
рекомендуется обобщить формулировку §1.2 до «самодостаточный рабочий стол
с ограниченным временем жизни» (см. §11).

### 2.2. Что переиспользуется из экосистемы

- `users`/`sessions` (БД `testing`) — **только** через SSO-шлюз: общая
  cookie `session_id` (`Domain=.bot-atelier.ru`) + внутренний endpoint
  `testing` `GET /api/internal/session`. Идентичность пользователя внутри
  подсистемы **неизвестна** (шлюз только проверяет сессию).
- Домен и TLS-конвенции: `/opt/<app>`, nginx-блок, certbot.
- Общая конвенция «На главную» (§6) и каталог портала (§8.1).

Ничего больше: `projects`, `bots`, `project_members`, `issues`, БД,
сервисы и страницы `testing` не используются; код других подсистем не
импортируется.

### 2.3. Рантайм: один Python-контейнер с in-process очередью

| Вариант | Оценка |
|---------|--------|
| (a) Python + Celery + Redis | Отвергнут: +2 контейнера (broker, worker), отдельный супервайзинг, persist-очередь — сложность не оправдана для малой команды и пачек в десятки файлов; Redis в экосистеме нет. |
| **(b) Один Python-контейнер, in-process asyncio-очередь** | **Выбран.** «Аналог» Redis/Celery по смыслу ТЗ №5: асинхронность, параллелизм 3–5, повторы, статусы — в одном процессе. Дух MVP `audio-correction` (один контейнер, in-process), но на asyncio; восстановление очереди после рестарта — из SQLite (§4.8). |
| (c) Node + Python-sidecar | Отвергнут: прецедент выведен из эксплуатации; два рантайма и IPC — максимальная сложность без выгод. |

Web-фреймворк: рекомендация — **FastAPI + uvicorn** (штатный multipart,
StaticFiles, async httpx); допустим эквивалент (aiohttp). Базовый образ
`python:3.12-slim`; **ffmpeg не нужен** — WAV передаётся в OpenAI как
есть, транскодирования нет. `ThreadingHTTPServer` из MVP недостаточен:
нужны конкурентные внешние вызовы и фоновый GC.

### 2.4. Структура репозитория

```text
transcribe/
  app/                      # исходники (собственный код, не вендор-копия)
    web_app.py              # HTTP API, статика UI, asyncio-очередь, воркеры
    pipeline.py             # стадии OpenAI (transcribe, label) + повторы
    twin24.py               # клиент Twin24: login / refresh / download
    storage.py              # SQLite, файлы workspace, TTL-GC, boot-recovery
    xlsx.py                 # XLSX (текстовый формат ячеек)
    static/index.html       # UI без сборки (один файл, inline CSS/JS)
    requirements.txt
    Dockerfile              # python:3.12-slim
    tests/                  # UUID-парсер, повторы, XLSX-формат, GC, статусы
  deploy/                   # артефакты выката (по образцу audio-correction)
    nginx.conf              # server-блок: SSO-шлюз + proxy 127.0.0.1:8082
    docker-compose.yml      # transcribe-app + volume transcribe-data
    deploy.sh               # по образцу deploy-mvp.sh (§8.5)
    DEPLOY.md               # DNS, certbot, health-check, rollback
```

На сервере: `/opt/transcribe/` (те же `app/` + `deploy/`) и
`/opt/transcribe/.env` (`OPENAI_API_KEY`, chmod 600, **в git не
попадает**).

### 2.5. Топология

```text

  │  https://transcribe.bot-atelier.ru
  ▼
nginx (TLS, SSO-шлюз)
  │ 1) auth_request ──▶ GET http://127.0.0.1:3000/api/internal/session

```

## 3. SSO-шлюз

### 3.1. Механизм

Дословно по образцу `correction-audio`:

- Общая cookie `session_id` (`HttpOnly`, `Secure`, `SameSite=Lax`,
  `Domain=.bot-atelier.ru`) ставит `testing`.
- nginx поддомена на **каждый** запрос выполняет `auth_request` к
  `testing: GET /api/internal/session` (loopback `127.0.0.1:3000`,
  заголовок `X-Internal-Auth: <INTERNAL_AUTH_TOKEN>`) и пропускает запрос
  к приложению (`127.0.0.1:8082`) только при `200`.
- Контракт внутреннего endpoint (коды `200/401/403/503`) — см.
  `.opencode/architecture/audio-correction.md` §3.3; endpoint loopback-only
  и закрыт снаружи nginx `testing`.
- Собственной сессии/кода аутентификации у подсистемы нет; рабочая cookie
  `transcribe_ws` — не аутентификация (§4.2).

### 3.2. Поток запроса и redirect

```text
Браузер                nginx (transcribe)              testing (loopback)
   │ GET /                     │                              │
   │──────────────────────────▶│ auth_request:                │
   │                           │ GET /api/internal/session ─▶ │
   │                           │ Cookie + X-Internal-Auth     │
   │                           │◀── 200/401/403/5xx ──────────│
   │ 200 → proxy 127.0.0.1:8082│                              │
   │ 401 → 302 на общий вход   │                              │
   │ 403 → 403 Forbidden       │                              │
   │ 5xx/недоступен → 503      │                              │
```

Redirect при `401`:

```text
https://bot-atelier.ru/login?next=https%3A%2F%2Ftranscribe.bot-atelier.ru%2F
```

### 3.3. Решение по 403 (отличие от deployed-конфига correction-audio)

По контракту внутреннего endpoint `403` означает: (1) неверный/отсутствующий
`X-Internal-Auth` — ошибка конфигурации шлюза, либо (2) `is_active = 0` —
деактивированный аккаунт. **Ни то, ни другое не исправляется повторным
входом**: редирект деактивированного пользователя на логин порождает
бесплодный цикл (вход → возврат → снова 403 → редирект), а редирект при
неверном секрете маскирует ошибку деплоя под «не вошли».

**Решение: в новом nginx-блоке 403 не перехватывается `error_page`** —
nginx отдаёт явный `403 Forbidden` (поведение `auth_request` по умолчанию).
Это соответствует документации `audio-correction.md` §3.2/§3.4 («403 → 403
Forbidden»). Текущий deployed-конфиг `correction-audio`
(`error_page 401 403 = @sso_login`) расходится с ней — рекомендуется
бэкпортировать исправление (§10, вопрос 5). Кастомная страница 403 с
текстом «Аккаунт деактивирован» — опционально позже, не в v1.

### 3.4. Режимы отказа

| Ситуация | Поведение |
|----------|-----------|
| `testing` недоступен | `auth_request` не проходит → `503`; недоступны и новые, и уже открытые вкладки (проверка на каждый запрос). |
| Общая cookie истекла/отозвана | `401` → redirect на вход экосистемы с `next`. |
| `is_active = 0` | `403 Forbidden` (§3.3). |
| Неверный `INTERNAL_AUTH_TOKEN` | `403` (или `503`, если секрет не задан в `testing`); ошибка конфигурации, видна явно. |
| Рестарт `transcribe-app` | Данные переживают (volume); очередь восстанавливается; токены Twin24 сбрасываются (§4.8). |
| Рестарт `testing` | Вход восстанавливается после подъёма; на состояние подсистемы не влияет. |

### 3.5. Cookie

| Cookie | Кто ставит | Назначение | Атрибуты |
|--------|-----------|------------|----------|
| `session_id` | `testing` | аутентификация в экосистеме | `Domain=.bot-atelier.ru`, `HttpOnly`, `Secure`, `SameSite=Lax` |
| `transcribe_ws` | `transcribe-app` | рабочий workspace (**не** аутентификация) | host-only, `HttpOnly`, `Secure`, `SameSite=Lax`, 32 hex |

Cookie независимы: шлюз не создаёт и не удаляет `transcribe_ws`.

## 4. Модель данных и состояния

### 4.1. Персистентность: выбор между (a) и (b)

| Аспект | (a) Полностью эфемерная (in-memory + tmp) | (b) Лёгкая персистентность (выбрано) |
|--------|-------------------------------------------|--------------------------------------|
| Длительность пачек | десятки файлов × 2 стадии × до 4 попыток × 30 с = десятки минут; рестарт посреди пачки теряет всё | переживается (SQLite + volume) |
| Цена рестарта | повторная загрузка/импорт + повторная оплата OpenAI + повторный ввод Twin24 | минимум: resume по стадиям |
| Требование ТЗ №5 («очистка … после выдачи Excel **или по TTL**») | TTL не нужен, но и результат живёт лишь до рестарта | TTL-GC — явная политика очистки |
| Операционная сложность | минимальная | чуть выше: volume + фоновый GC |
| Соответствие §1.2 AGENTS.md | буквально «эфемерный рабочий стол» | «самодостаточный рабочий стол с ограниченным временем жизни»; фиксируется этим документом |

**Выбор (b).** ТЗ прямо требует TTL-очистку — она предполагает выживание
состояния между запросами; при полностью эфемерной модели любой деплой/OOM
обнулял бы оплаченную работу. Токены Twin24 при этом — **исключительно в
RAM** (пароль и токены на диск не попадают никогда).

### 4.2. Идентификаторы и изоляция

- `workspace_id` = cookie `transcribe_ws` (`uuid4().hex`, 32 hex),
  создаётся лениво при первом обращении. Workspace не привязан к
  идентичности пользователя (шлюз её не передаёт) — как `acoustic_session`.
- `file_id` = `uuid4`.
- `dialog_id`: для Twin24 — UUID из строки/ссылки, нормализуется к нижнему
  регистру; для загрузки — имя файла без расширения (как есть).
- `UNIQUE (workspace_id, dialog_id)`: дубликат отклоняется с ошибкой по
  конкретному файлу/строке, не блокируя остальные.

### 4.3. Схема SQLite (`/data/transcribe.db`, режим WAL)

- `workspaces`: `id` TEXT PK, `created_at`, `last_seen_at`,
  `delivered_at` NULL (время первой выдачи XLSX).
- `files`: `id` TEXT PK, `workspace_id` FK, `dialog_id`, `source`
  (`upload` | `twin24`), `status` (`queued` | `transcribing` | `labeling`
  | `done` | `error`), `error` NULL, `transcript` NULL (сырой текст
  стадии 1 — **промежуточное** хранилище по ТЗ №2, удаляется после выдачи),
  `result_text` NULL (размеченный итог для XLSX, живёт до TTL),
  `audio_path` NULL (относительный путь WAV, NULL после очистки),
  `original_name` NULL, `size_bytes`, `created_at`, `updated_at`.
  `UNIQUE (workspace_id, dialog_id)`; индекс `(workspace_id, status)`.

Промежуточное хранилище пайплайна — **БД** (столбец `transcript`),
записывается немедленно по завершении стадии 1 и служит точкой
восстановления.

### 4.4. Файлы на диске (volume `transcribe-data`)

```text
/data/
  transcribe.db
  work/<workspace_id>/
    audio/<file_id>.wav     # исходный WAV (оба сценария)
```

- Загрузка: multipart → `audio/<file_id>.wav` (имя на диске — `file_id`,
  оригинал — в БД).
- Twin24: серверное скачивание → тот же путь; конвертации нет.
- В отличие от MVP (`tempfile.mkdtemp`), путь детерминирован
  `/data/work/<ws>/` — он должен переживать рестарт и быть находимым из БД.
- XLSX на диске **не хранится**: генерируется во временный файл при
  запросе и отдаётся стримом; повторный запрос регенерируется из
  `result_text`.

### 4.5. Токены Twin24 (только RAM)

- `TWIN24: dict[workspace_id → {email, token, refresh_token, expires_at}]`
  — в памяти процесса; **не** в БД, не на диске, не в логах.
- `ttl` логина — всегда `86400` (максимум; у пользователя не спрашиваем).
- Авто-refresh: (1) проактивно — перед вызовом, если `now ≥ expires_at −
  60 с`; (2) реактивно — при `401` от Twin24 (один повтор через refresh).
  Предполагаемый контракт refresh — `POST /iam/api/v1/auth/refresh
  {refreshToken}` → `{token, refreshToken}`; уточнить (§10, вопрос 2).
- Рестарт процесса: словарь пуст; UI показывает Twin24 «не подключён»;
  уже скачанные файлы и результаты не теряются.
- Пароль: принимается одним `POST /api/twin24/login`, используется один
  раз, нигде не сохраняется и не логируется.

### 4.6. Статусная модель и очередь

- Статусы файла и русские метки UI: `queued` «в очереди» →
  `transcribing` «транскрибируется» → `labeling` «размечаются роли» →
  `done` «готово» / `error` «ошибка».
- Скачивание из Twin24 выполняется воркером в начале стадии
  `transcribing` (для пользователя — «транскрибируется»); неудача
  скачивания → `error` по файлу («не удалось скачать из Twin24: …»),
  пачка продолжает обрабатываться.
- Очередь: `asyncio.Queue` + пул задач-воркеров (`TRANSCRIBE_WORKERS`,
  по умолчанию 4, кламп 3–5). Одна задача = один файл: [download] →
  transcribe → label. Тем самым параллелизм запросов к OpenAI = 3–5.
- Терминальные состояния: `done`, `error`. `all_terminal` = в workspace
  есть ≥1 файла и все терминальны → UI показывает кнопку Excel.

### 4.7. Очистка (ТЗ №5)

- **После выдачи:** при первой успешной выдаче XLSX ставится
  `workspaces.delivered_at`; немедленно удаляются все WAV
  (`audio_path` → NULL) и промежуточные `transcript` (→ NULL).
  `result_text` и `dialog_id` остаются до TTL — повторное скачивание
  XLSX работает.
- **TTL-GC:** фоновая задача каждые 10 мин; workspace с
  `last_seen_at < now − 24 ч` удаляется целиком (строки файлов, строка
  workspace, каталог `/data/work/<ws>`). `last_seen` обновляется каждым
  API-запросом workspace.
- Защита диска: soft-лимит 1 ГБ аудио на workspace — при превышении новые
  загрузки отклоняются с понятной ошибкой (число — §10, вопрос 3).

### 4.8. Поведение при рестарте

| Что | Где живёт | Рестарт контейнера / деплой |
|-----|-----------|------------------------------|
| Токены Twin24 | RAM | сбрасываются → «переподключите Twin24» для новых импортов |
| In-process очередь | RAM | восстанавливается из БД при старте (boot-recovery) |
| Состояния задач, результаты | SQLite (volume) | сохраняются |
| WAV | volume | сохраняются (до выдачи/TTL) |

**Boot-recovery при старте:** файлы со статусами `transcribing`/`labeling`
переводятся в `queued` и пере-ставятся в очередь (с дедупликацией по
`file_id`); если `transcript` уже сохранён — стадия 1 пропускается,
файл сразу идёт в разметку (экономия вызовов OpenAI).

### 4.9. Что видит вернувшийся пользователь

- **Тот же браузер, до TTL:** свою пачку — статусы, ошибки, результаты;
  кнопка Excel доступна при `all_terminal`. Twin24-подключение сброшено
  только если был рестарт контейнера (переподключить при нужде новых
  импортов).
- **После TTL (24 ч неактивности):** пустой рабочий стол (cookie остаётся,
  но workspace удалён — создастся новый).
- **Другой браузер/устройство:** новый пустой workspace — идентичность не
  привязана к пользователю экосистемы (осознанное ограничение, как у
  `acoustic_session`; см. §9).
- Переход «На главную» и возврат ничего не удаляют.

## 5. UI и API

### 5.1. UI (без сборки)

`static/index.html`, inline CSS/JS, без внешних CDN — по духу MVP. Шапка:
название подсистемы + анкер «← На главную» (§6).

- **Панель А «Локальные файлы»:** multi-select `.wav`; отправка
  последовательными POST по одному файлу (естественный per-file прогресс и
  ошибки).
- **Панель Б «Twin24»:** форма email/password (`type=password`; после
  логина поле очищается — пароль не хранится); textarea для строк (UUID
  и/или ссылки `https://twin24.ai/app/download/records/{UUID}/`, построчно);
  ответ сервера — принятые/отклонённые строки с причинами.
- **Таблица файлов:** ID диалога / источник (файл | Twin24) / статус
  (русские метки §4.6) / текст ошибки. Polling `GET /api/state` каждые 3 с,
  пока есть нетерминальные файлы.
- **Кнопка «Скачать результат (Excel)»** — появляется при `all_terminal`;
  ведёт на `GET /api/export`.
- Смешивание сценариев А и Б в одном workspace разрешено: один XLSX на
  всю пачку.

### 5.2. API

| Метод | Путь | Назначение |
|-------|------|------------|
| GET | `/` | UI |
| GET | `/api/health` | `{"status":"ok"}` — health-check для deploy-скрипта (loopback) |
| GET | `/api/state` | файлы (`id`, `dialog_id`, `source`, `status`, `error`), `twin24: {connected}`, `all_terminal`, лимиты |
| POST | `/api/files` | один WAV (multipart, поле `file`) ≤ 25 МБ → файл `queued`; 413/400 с текстом ошибки |
| POST | `/api/twin24/login` | `{email, password}` → `{connected: true}`; `ttl=86400` фикс. |
| POST | `/api/twin24/import` | `{lines}` → `{accepted: [{uuid, file_id}], rejected: [{line, reason}]}`; `409`, если Twin24 не подключён |
| GET | `/api/export` | XLSX; `409`, пока не все файлы терминальны; первая успешная выдача запускает очистку §4.7 |

Все endpoint (кроме `/api/health`) ключуются cookie `transcribe_ws`
(создаётся лениво). Наружу — только через nginx-шлюз.

### 5.3. Сценарий А: локальная мультизагрузка

- UI: multi-select; последовательные `POST /api/files` по одному.
- Серверные проверки: расширение `.wav` (регистронезависимо), размер
  ≤ 25 МБ, лимит 50 файлов, лимит 1 ГБ, дубликат `dialog_id`. Отказ по
  одному файлу не блокирует остальные.
- `dialog_id` = имя файла без расширения.

### 5.4. Сценарий Б: Twin24

- **Логин:** `POST https://twin24.ai/iam/api/v1/auth/login`
  `{email, password, ttl: 86400}` → `{token, refreshToken}`; хранение —
  RAM (§4.5); пароль не сохраняется и не логируется.
- **Импорт строк:** сервер парсит textarea построчно:
  (1) ссылка `^https://twin24\.ai/app/download/records/<UUID>/?$` → UUID;
  (2) «голый» UUID; регэксп UUID:
  `[0-9a-fA-F]{8}-[0-9a-fA-F]{4}-[0-9a-fA-F]{4}-[0-9a-fA-F]{4}-[0-9a-fA-F]{12}`;
  (3) иначе — строка в `rejected` с причиной («не UUID и не ссылка»).
  Валидные → файлы `queued` (скачает воркер). До 50 строк за запрос.
- **Скачивание:** `GET https://twin24.ai/app/download/records/{UUID}/`
  с токеном Twin24 (точный контракт — §10, вопрос 1; ожидаем WAV).
  Неудача скачивания или 401-после-refresh → файл `error`, пачка не
  блокируется.

### 5.5. Пайплайн (на файл)

1. **(только twin24)** скачивание WAV (подшаг стадии `transcribing`).
2. **`gpt-4o-transcribe`** (`/v1/audio/transcriptions`, файл WAV as-is):
   таймаут попытки 30 с; первая попытка + до 3 повторов; паузы между
   попытками 2/4/6 с. Успех → `transcript` немедленно в БД (точка
   восстановления). Финальная неудача → `error` «транскрибация не
   удалась после 3 повторов (…)».
3. **`gpt-4o-mini`** (chat.completions, `temperature=0`): разметка ролей
   Оператор/Клиент; формат вывода — строки «Оператор: …» / «Клиент: …»
   (детали промпта — §10, вопрос 6). Те же повторы. Успех →
   `result_text`, статус `done`.

Порядок — FIFO; параллелизм 3–5 (§4.6). Логирование вызовов — §7.

### 5.6. XLSX

- openpyxl; один лист; шапка: «ID диалога» | «Текст транскрибации».
- Колонка A: `dialog_id` строкой + **принудительно текстовый формат
  ячейки** (`number_format = '@'`) — защита UUID и числоподобных имён
  файлов от автопреобразования Excel.
- Колонка B: `result_text`; при `error` — текст ошибки (например,
  «ОШИБКА: …») — по ТЗ №3, частичные ошибки не блокируют выдачу.
- Порядок строк — порядок добавления файлов в пачку.
- Имя файла: `transcribe-<ГГГГММДД>-<ЧЧММСС>.xlsx`, `Content-Disposition:
  attachment`. Генерируется из БД при каждом запросе, на диске не
  хранится (§4.4).

## 7. Безопасность

- **Секреты:**
  - `OPENAI_API_KEY` — env контейнера из `/opt/transcribe/.env`
    (chmod 600, не в git); прецедент подачи внешних AI-ключей — env.
  - `INTERNAL_AUTH_TOKEN` — nginx-шлюз (sed-подстановка из
    `/root/.internal_auth_token` при выкате); совпадает с
    `.env.production` `testing`; в git не попадает.
  - Пароль Twin24 — только в одном POST-запросе; не сохраняется, не
    логируется (в т.ч. не попадает в логирование тел запросов).
- **Логирование внешних вызовов (Twin24, OpenAI):** метод, путь,
  HTTP-статус, длительность, размер, номер попытки,
  `workspace_id`/`file_id`. **Запрещено логировать:** пароль,
  `token`/`refreshToken`, заголовок `Authorization`, `OPENAI_API_KEY`,
  содержимое транскриптов и аудио. Логи — stdout (`docker logs`).
- **Конфиденциальность звонков:** содержимое не логируется; аудио и тексты
  живут ≤ TTL, удаляются после выдачи; доступ — только у владельца cookie
  (32 hex, host-only, `HttpOnly`, `Secure`) за SSO-шлюзом.
- **Сеть:** приложение слушает только `127.0.0.1:8082`; наружу — только
  через nginx-шлюз; `/api/internal/*` не вызываются подсистемой.
- **Стоимость OpenAI:** лимиты файла/пачки/объёма, параллелизм 3–5, повторы
  ≤3; stage-resume после рестартов (§4.8) сокращает повторную оплату.
- **Изоляция workspace:** без cookie доступ к чужому `file_id`/`workspace_id`
  невозможен (все запросы ключуются своей cookie).

### 8.4. nginx-блок (`deploy/nginx.conf`, ориентир)

```nginx
server {
    listen 80;
    server_name transcribe.bot-atelier.ru;

    # Один WAV ≤ 25 МБ + multipart-оверхед (UI шлёт файлы по одному).
    client_max_body_size 30M;

    # --- SSO-шлюз (по образцу correction-audio) ------------------------
    auth_request /_sso;

    # 401 → общий вход экосистемы с возвратом на поддомен.
    error_page 401 = @sso_login;

    # 403 НЕ перехватываем (§3.3): деактивированный аккаунт или неверный
    # секрет шлюза не лечатся повторным входом — явный 403 Forbidden.
    # error_page для 403 не определяется — nginx вернёт 403 по умолчанию.

    # Недоступность testing / ошибки внутреннего endpoint → 503.
    error_page 500 502 503 504 = @sso_unavailable;

    location = /_sso {
        internal;
        proxy_pass http://127.0.0.1:3000/api/internal/session;
        proxy_pass_request_body off;
        proxy_set_header Content-Length "";
        proxy_set_header Cookie $http_cookie;
        proxy_set_header X-Internal-Auth "<INTERNAL_AUTH_TOKEN>";
    }

    location @sso_login {
        return 302 https://bot-atelier.ru/login?next=https%3A%2F%2Ftranscribe.bot-atelier.ru%2F;
    }

    location @sso_unavailable {
        return 503;
    }

    # --- Приложение -----------------------------------------------------
    location / {
        proxy_pass http://127.0.0.1:8082;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_request_buffering off;
        proxy_read_timeout 900s;
    }
}
```

Примечание: собственные 5xx-ответы приложения проходят насквозь
(`proxy_intercept_errors` по умолчанию off); ошибки **соединения** с
приложением (502/504) перехватываются в 503 — для пользователя единая
семантика «недоступно», в логах различимо.

### 8.5. `deploy.sh` (по образцу `deploy-mvp.sh`)

1. `docker compose up -d --build` (в `/opt/transcribe/deploy`);
2. ждать `curl http://127.0.0.1:8082/api/health` (до 30 × 2 с);
3. `INTERNAL_AUTH_TOKEN` из env или `/root/.internal_auth_token`;
4. `sed`-подстановка `<INTERNAL_AUTH_TOKEN>` →
   `/etc/nginx/sites-available/transcribe.bot-atelier.ru` + symlink в
   `sites-enabled`;
5. `nginx -t && systemctl reload nginx`.

`DEPLOY.md`: DNS (§8.2), создание `/opt/transcribe/.env`, выкат,
проверка SSO-сценариев (без cookie → 302 на вход; с cookie → UI;
`is_active=0` → 403; `testing` остановлен → 503 и новые, и открытые
вкладки), проверка «← На главную», rollback.

### 8.6. Rollback

1. `docker compose down` (volume `transcribe-data` **оставить** — данные
   пользователей);
2. удалить symlink и файл `sites-available/transcribe.bot-atelier.ru`,
   `nginx -t && systemctl reload nginx`;
3. `git revert` каталога `transcribe/` и записи портала;
4. при полном выводе по решению владельца — `docker volume rm
   transcribe-data` (данные пользователей будут потеряны);
5. TLS-сертификат можно оставить (не мешает).

## 9. Риски и ограничения

1. **Жёсткая runtime-зависимость от `testing`** — при недоступности
   подсистема целиком отдаёт 503, включая открытые вкладки (как у
   `correction-audio`).
2. **30-секундный таймаут транскрибации** может не хватать на длинные
   файлы (25 МБ WAV ≈ ~26 мин при 8 кГц mono / ~13 мин при 16 кГц mono /
   ~2,5 мин при 44,1 кГц стерео) → ложные `error`. Смягчение: рекомендация
   загружать телефонные WAV 8–16 кГц mono; чанкинг — §10, вопрос 4.
3. **Стоимость OpenAI:** повторы и пере-постановки после рестартов
   увеличивают расход; stage-resume (§4.8) и лимиты смягчают.
4. **Неизвестный контракт Twin24** (download/refresh) — риск правок при
   интеграции; изолирован в `twin24.py`.
5. **Один контейнер:** нет горизонтального масштабирования; достаточно для
   небольшой команды (осознанный выбор §2.3).
6. **Диск:** WAV-пачки; лимиты (50 файлов / 1 ГБ / TTL 24 ч) + GC каждые
   10 мин; нужен мониторинг `/data`.
7. **Workspace не привязан к идентичности:** смена браузера/устройства =
   новый пустой стол; нет cross-device и «моих пачек» (следствие
   SSO-шлюза, который не передаёт идентичность).
8. **5xx от приложения и от `testing`** для пользователя неразличимы
   (оба → 503); различимо в логах (§8.4).
9. **`OPENAI_API_KEY` в env на сервере** — единая точка утечки; ротация
   вручную.
10. **PII звонков:** смягчено TTL, удалением после выдачи и запретом
    логирования содержимого (§7).

## 11. Черновик будущей секции AGENTS.md (после одобрения пользователем)

> Вставить как §5 «Подсистема: transcribe (транскрибация звонков)»;
> одновременно: (а) обобщить в §1.2 «независимый эфемерный рабочий стол»
> до «самодостаточный рабочий стол с ограниченным временем жизни (TTL)»;
> (б) дополнить список подсистем в §4 портала.

**Статус:** самостоятельная подсистема на поддомене
`transcribe.bot-atelier.ru` (контейнер `transcribe-app`, loopback
`127.0.0.1:8082`, volume `transcribe-data`) за nginx SSO-шлюзом по образцу
`audio-correction`. Самодостаточный рабочий стол с ограниченным временем
жизни (TTL 24 ч): лёгкая персистентность (SQLite + WAV в docker-volume),
без проектной модели.

**Цель:** дать аутентифицированному пользователю собрать пачку записей
звонков (локальные WAV и/или импорт из ЛК Twin24), асинхронно прогнать её
через `gpt-4o-transcribe` и разметку ролей `gpt-4o-mini` (Оператор/Клиент)
и скачать единый XLSX («ID диалога» + «Текст транскрибации»); данные
удаляются после выдачи или по TTL.

**Границы модуля:**

- Исходники: `transcribe/app/` (`web_app.py`, `pipeline.py`, `twin24.py`,
  `storage.py`, `xlsx.py`, `static/index.html`, `Dockerfile`, `tests/`).
- Артефакты деплоя: `transcribe/deploy/` (`nginx.conf`,
  `docker-compose.yml`, `deploy.sh`, `DEPLOY.md`).
- Не зависит от `testing` за пределами SSO; не использует `projects`,
  `bots`, `project_members`, `issues`, БД/сервисы/страницы `testing`.
- Единственная связь — SSO (общая cookie + внутренний endpoint).

**SSO:** nginx `auth_request` к `testing: GET /api/internal/session`;
`401` → общий вход; `403` → явный 403 Forbidden; недоступность `testing`
→ 503. Собственной сессии нет; рабочая cookie `transcribe_ws` (32 hex,
HttpOnly, host-only) — не аутентификация.

**Модель данных (без проектов):**

- SQLite `/data/transcribe.db` (volume): `workspaces` (`id`,
  `created_at`, `last_seen_at`, `delivered_at`), `files` (`id`,
  `workspace_id`, `dialog_id`, `source`, `status`, `error`, `transcript`,
  `result_text`, `audio_path`, `original_name`, `size_bytes`, …),
  `UNIQUE (workspace_id, dialog_id)`.
- Статусы: `queued` → `transcribing` → `labeling` → `done`/`error`.
- WAV: `/data/work/<workspace_id>/audio/<file_id>.wav`.
- Токены Twin24: только в памяти процесса; пароль не хранится.
- Очистка: WAV и сырые транскрипты — после первой выдачи XLSX; workspace
  целиком — TTL-GC через 24 ч неактивности (GC каждые 10 мин).

**UI и API:** `static/index.html` без сборки; `GET /api/state` (polling),
`POST /api/files` (один WAV ≤ 25 МБ), `POST /api/twin24/login`,
`POST /api/twin24/import` (строки UUID/ссылок, построчная валидация),
`GET /api/export` (XLSX при all-terminal), `GET /api/health`. Пайплайн:
`gpt-4o-transcribe` (30 с, ≤3 повторов, паузы 2/4/6 с) → `gpt-4o-mini`
(temperature=0, «Оператор/Клиент»); параллелизм 3–5.

**Что переиспользует из общего каркаса:** `users`/`sessions` через
SSO-шлюз; домен/TLS-конвенции (`/opt/<app>`, nginx-блок, certbot); запись
в `portal/subsystems.js`; конвенцию «На главную».

**Что уникально:** интеграция Twin24 (login/refresh/download, пароль не
хранится); двухстадийный OpenAI-пайплайн с повторами; in-process
asyncio-очередь (3–5 воркеров) без Redis/Celery; XLSX-экспорт с
принудительно текстовым форматом ячеек; первая подсистема с лёгкой
персистентностью и TTL-GC.

**Решённые продуктовые вопросы:**

1. **Доступ** — все активные пользователи всех ролей через SSO; проектной
   модели нет.
2. **Классификация** — самостоятельная подсистема (не модуль `testing`).
3. **Персистентность** — лёгкая: SQLite + volume, TTL 24 ч; токены Twin24
   — только RAM.
4. **Очередь** — in-process asyncio, воркеры 3–5; Redis/Celery не вводится.
5. **Лимиты** — 25 МБ/файл, 50 файлов/пачку, 1 ГБ аудио/workspace, TTL 24 ч.
6. **Очистка** — после выдачи Excel и по TTL.
7. **403 шлюза** — явный 403 Forbidden (без редиректа).
8. **Название** — `transcribe` / «Транскрибация звонков» /
   `transcribe.bot-atelier.ru`.
