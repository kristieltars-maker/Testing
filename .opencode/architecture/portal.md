# Архитектура портала экосистемы `portal` (`bot-atelier.ru`)

> **Статус:** новый общий (ecosystem-level) компонент. Портал — публичная
> точка входа экосистемы, с которой пользователь выбирает подсистему.
> **Язык документа:** русский.
> **Назначение:** форма портала, структура репозитория, хостинг/DNS/TLS,
> модель аутентификации, навигация «На главную» из подсистем, риски.
> **Связанные документы:** `AGENTS.md` §1 (общий каркас), §4 (портал),
> `.opencode/architecture/audio-correction.md`,
> `.opencode/architecture/audio-correction-standalone.md`.
>
> **Только архитектура.** Здесь нет кода; команды и разметка приведены как
> ориентир для будущего плана реализации.

---

## 1. Резюме решений

| Вопрос | Решение |
|--------|---------|
| **Домен** | `bot-atelier.ru` (apex) + `www.bot-atelier.ru`. |
| **Форма** | **Статический сайт** без сборки, без SPA-фреймворка, без backend. |
| **Назначение** | Публичная посадочная страница: заголовок экосистемы + карточки подсистем. Сейчас: `testing`, `correction-audio`. |
| **Backend** | **Не нужен.** Ни API, ни сессий, ни БД, ни PM2-процесса. |
| **Хостинг** | nginx, статика из `/opt/portal/`. |
| **TLS** | `certbot --nginx -d bot-atelier.ru -d www.bot-atelier.ru`. |
| **Аутентификация портала** | Нет. Страница публичная и не читает и не меняет общую сессию. |
| **Действие «Войти»** | Ссылка на общий вход экосистемы: `https://bot-atelier.ru/login?next=https://bot-atelier.ru/`. |
| **Идентичность пользователя** | На портале **не показывается** (общая cookie `session_id` — `HttpOnly`). |
| **Переход в подсистему** | Обычные ссылки на `https://testing.bot-atelier.ru/` и `https://correction-audio.bot-atelier.ru/`; SSO срабатывает в подсистеме. |
| **«На главную»** | Plain-анкер на `https://bot-atelier.ru/` в шапке каждой подсистемы; **без** выхода из аккаунта. |
| **Секреты** | На портале отсутствуют. Внутренние endpoint'ы и токены не используются. |

## 2. Форма портала: почему статический сайт

### 2.1. Рассмотренные варианты

| Вариант | Плюсы | Минусы |
|---------|-------|--------|
| **A. Статический HTML/CSS (+ минимальный module-JS)** | Нет сборки, нет зависимостей, нет PM2, нет БД. Деплой = копирование файлов. Не может ничего «сломать» в сессии. Быстро и кэшируемо. | Нет динамической идентичности пользователя (не нужна). Список подсистем надо обновлять вручную. |
| **B. Собранное SPA (React + Vite)** | Единый стек с `testing`/`audio-correction`; можно добавить роутинг, тему, счётчики. | `node_modules`, lockfile, билд-шаг, версионирование ассетов, риск «забыли пересобрать». Всё это ради страницы с двумя ссылками. Идентичность всё равно недоступна без backend (HttpOnly). |
| **C. SSR/backend-портал (Node + шаблоны)** | Мог бы читать `session_id` через loopback `testing` и показывать имя. | Новый сервис, порт, PM2-процесс, рантайм-зависимость от `testing`, деплой и мониторинг. Противоречит «низкой поддержке». |

### 2.2. Рекомендация — вариант A

**Рекомендуется статический сайт.** Обоснование:

- **Задача портала статична.** Это список подсистем и ссылка на вход. Ни
  данных, ни состояния, ни авторизации — backend нечего обслуживать.
- **Низкая поддержка.** Нет `node_modules`, сборки, PM2-процесса, БД,
  миграций, обновления зависимостей. Обновление портала — правка одного
  HTML/CSS-файла и перезагрузка nginx (или даже без него — статика
  отдаётся сразу).
- **Безопасность.** Портал не трогает cookie `session_id`, не вызывает
  `/api/internal/*`, не хранит секретов. У него нулевая площадь атаки,
  кроме самой статики.
- **Безопасно для сессии.** «Не разлогинивать» гарантируется тем, что
  портал физически не выполняет `POST /auth/logout` и не меняет cookie.
  SPA здесь ничего не добавляет.
- **Расширяемость достижима без сборки.** Каталог подсистем — это
  небольшой массив в `subsystems.js`; новая подсистема = одна запись.
  Этого достаточно, а полноценный SPA/роутер избыточен.

> **Если позже потребуется показывать имя пользователя** на портале —
> это единственная причина добавить backend. Тогда: отдельный маленький
> Node-сервис, который по loopback дергает `testing: GET /api/internal/session`
> с `X-Internal-Auth`, рендерит/отдаёт `{ user }` и не заводит собственной
> сессии. Это осознанно **вне** текущей архитектуры (см. §7).

## 3. Структура репозитория

```text
portal/                        # корень портала (в монорепозитории)
  index.html                   # публичная посадочная страница + inline module-скрипт
  styles.css                   # оформление (карточки подсистем, адаптив)
  subsystems.js                # каталог подсистем (единственное место для правок при добавлении)
  assets/
    logo.svg                   # логотип экосистемы (опционально)
    favicon.ico                # иконка (опционально)
  nginx.conf                   # референс server-блока (копия на сервере)
  DEPLOY.md                    # DNS, nginx, certbot, обновление (ориентир)
```

Назначение файлов:

- **`index.html`** — семантическая разметка: заголовок экосистемы,
  подзаголовок, кнопка «Войти», контейнер `<ul id="subsystems">` под
  карточки, `<noscript>`-фолбэк со ссылками на подсистемы, подключение
  `subsystems.js`/рендер. Никаких фреймворков и внешних CDN.
- **`styles.css`** — локальные стили; без внешних шрифтов/CDN, чтобы
  страница работала без сторонних доменов.
- **`subsystems.js`** — экспортирует массив записей каталога:

  ```js
  // Структура одной записи (без кода: контракт данных)
  {
    slug: 'testing',                       // стабильный идентификатор
    title: 'Тестирование ботов',           // отображаемое имя
    description: 'Трекинг замечаний…',     // короткое описание
    url: 'https://testing.bot-atelier.ru/' // абсолютный URL подсистемы
  }
  ```

  Текущие записи: `testing` и `correction-audio`. Добавление подсистемы —
  одна новая запись; порядок карточек = порядок в массиве.
- **`nginx.conf`** — референсная копия блока из §4.2 (в репозитории, как
  это уже сделано для `testing`).
- **`DEPLOY.md`** — пошаговый ориентир (DNS, nginx, certbot, обновление).

**Соглашение:** портал не импортирует код подсистем и не зависит от их
сборок. Единственная связь — ссылки и общий домен/SSO.

## 4. Хостинг: DNS, nginx, TLS

### 4.1. DNS (зона `bot-atelier.ru`, reg.ru)

| Имя | Тип | Значение | Назначение |
|-----|-----|----------|------------|
| `@` (apex) | `A` | `2.26.112.123` | Портал. **Сейчас указывает на `95.163.244.138` — требуется перенаправление.** |
| `www` | `A` (или `CNAME` → `bot-atelier.ru`) | `2.26.112.123` | Портал (или редирект на apex, см. ниже). |
| `*` (wildcard) | `A` | `2.26.112.123` | Уже настроен; поддомены не затрагиваются. |

Проверка:

```bash
nslookup bot-atelier.ru
nslookup www.bot-atelier.ru
```

> **Важно:** до перенаправления apex TLS для `bot-atelier.ru` выпустить
> нельзя — HTTP-01 проверка certbot требует, чтобы имя резолвилось на
> сервер. Wildcard-запись не покрывает apex (apex — не поддомен).

### 4.2. Server-блок nginx

Файл: `/etc/nginx/sites-available/bot-atelier.ru`.

```nginx
server {
    listen 80;
    server_name bot-atelier.ru www.bot-atelier.ru;

    root /opt/portal;
    index index.html;

    # index.html — без кэша (чтобы обновления подхватывались сразу).
    location = /index.html {
        add_header Cache-Control "no-cache, no-store, must-revalidate";
        add_header Pragma "no-cache";
        expires -1;
    }

    # Каталог подсистем — тоже без длинного кэша (правится чаще всего).
    location = /subsystems.js {
        add_header Cache-Control "no-cache, no-store, must-revalidate";
        expires -1;
    }

    # Статика/ассеты — можно кэшировать долго.
    location /assets/ {
        expires 30d;
        add_header Cache-Control "public";
    }

    location / {
        try_files $uri $uri/ /index.html;
    }
}
```

Особенности:

- **Один блок на два имени** (`bot-atelier.ru` и `www`). Это упрощает
  certbot (один сертификат на оба `-d`) и не ломает выпуск при разных
  server-блоках.
- **Нет `/api`, нет `client_max_body_size`, нет proxy** — портал не
  обслуживает динамику.
- **Нет PM2 и Node.** Статику отдаёт nginx.
- **`www`** отдаёт тот же контент; канонизация — через
  `<link rel="canonical" href="https://bot-atelier.ru/">` в `index.html`.
  Опционально можно добавить `if ($host = www.bot-atelier.ru) { return 301 https://bot-atelier.ru$request_uri; }` — но только после успешного
  выпуска сертификата (см. §4.4).

Подключение:

```bash
ln -sf /etc/nginx/sites-available/bot-atelier.ru \
       /etc/nginx/sites-enabled/bot-atelier.ru
nginx -t && systemctl reload nginx
```

### 4.3. Деплой статики

```text
/opt/portal/
  index.html
  styles.css
  subsystems.js
  assets/
```

Способ доставки — по конвенции проекта (`scp`/`git pull`/распаковка
релиза). Билд не требуется. После копирования файлов nginx перезагружать
не нужно (статика читается с диска); `reload` нужен только при изменении
самого server-блока.

### 4.4. Сертификат

```bash
certbot --nginx -d bot-atelier.ru -d www.bot-atelier.ru \
  --non-interactive --agree-tos --email admin@bot-atelier.ru
```

Certbot сам добавит `listen 443 ssl`, ссылки на сертификат и редирект с
`80` для обоих имён. Автопродление — штатный таймер certbot. Портал на
поддомены не влияет: их существующие сертификаты не трогаются.

> **Порядок:** сначала DNS-перенаправление apex + `www`, дождаться
> propagation, затем nginx-блок, затем certbot. Если сделать certbot
> раньше — HTTP-01 не пройдёт.

## 5. Аутентификация портала

### 5.1. Модель

- Портал **публичный**: любой visitor видит каталог подсистем.
- Портал **не имеет** собственной сессии, cookie, `/login`-страницы,
  logout-действия и backend.
- Портал **не читает и не пишет** общую cookie `session_id`
  (`HttpOnly`) и локальные cookie подсистем.
- Переход в подсистему — обычная навигация. Если пользователь уже вошёл,
  SSO внутри подсистемы подхватывает общую cookie:
  - `testing`: `GET /api/me` по общей сессии → сразу рабочий интерфейс;
  - `correction-audio`: nginx SSO-шлюз (`auth_request` к
    `testing: GET /api/internal/session`) пропускает запрос к MVP;
    локальной сессии подсистемы нет.
- Если пользователь **не** вошёл, подсистема сама уводит его на общий
  вход (`testing` — `ProtectedRoute → /login`; `correction-audio` — `302`
  от nginx-шлюза на `testing/login?next=…`).

### 5.2. Действие «Войти»

Кнопка «Войти» — ссылка на общий вход экосистемы с возвратом на портал:

```text
https://bot-atelier.ru/login?next=https%3A%2F%2Fbot-atelier.ru%2F
```

Существующий `LoginPage.jsx` в `testing` уже поддерживает whitelisted
параметр `next` (`isAllowedNext`: разрешены `bot-atelier.ru` и
`*.bot-atelier.ru`), поэтому `next` на apex корректен и защищён от open
redirect. После успешного входа пользователь возвращается на портал.

> **Кнопка «Войти» — вторичная.** Основные действия портала — карточки
> подсистем. «Войти» полезна как явный вход и как возврат на портал
> после логина.

### 5.3. Идентичность пользователя

Общая cookie `session_id` — `HttpOnly`, поэтому клиентский JS портала
**не может** прочитать её или узнать имя/роль пользователя. Попытка
«угадать» вход по наличию cookie с клиента невозможна.

**Рекомендация (самый простой корректный подход): не показывать имя
пользователя на портале.** Страница всегда выглядит одинаково для
гостя и для вошедшего. Идентичность отображают подсистемы (у них есть
`/api/me`). Это честно, безопасно и не требует backend.

Альтернатива (вне текущей архитектуры): маленький backend портала,
который читает cookie по loopback через `testing: GET /api/internal/session`
(shared secret, только с сервера) и рендерит имя. См. §7.

### 5.4. Секреты

На портале секретов нет и не должно быть:

- Нет `INTERNAL_AUTH_TOKEN`, ключей, DSN, учётных данных.
- Портал не вызывает `/api/internal/*` (эти endpoint'ы закрыты снаружи
  nginx `deny all` и слушают только loopback).
- Никакие токены/пароли не попадают в HTML/JS. `subsystems.js` содержит
  только публичные URL подсистем.
- Портал не логирует и не собирает персональные данные.

## 6. Навигация «На главную» из подсистем

### 6.1. Общий принцип

- «На главную» — это **plain-анкер** `<a href="https://bot-atelier.ru/">`,
  а не `<Link>` React Router (переход кросс-доменный).
- Анкер **не** вызывает `logout()`, `POST /auth/logout`,
  `DELETE /session` или иной сброс состояния. Общая cookie `session_id`
  (`Domain=.bot-atelier.ru`) и локальная сессия подсистемы сохраняются.
- Переход не завершает и не очищает workspace `correction-audio`
  (TTL/GC продолжают работать как обычно; активность обновится при
  следующем обращении).

### 6.2. `testing` (PM2 `testing-bots`)

| Файл | Что делается |
|------|--------------|
| `frontend/src/App.jsx` | В компоненте `Layout` (навигационная панель) добавить ссылку «На главную» на портал. |
| `frontend/src/constants/ecosystem.js` *(новый, опционально)* | `export const PORTAL_URL = 'https://bot-atelier.ru/';` — единая константа вместо литерала. |

Расположение: в `<nav>` рядом с брендом «Тестирование ботов», до блока
пользователя. Это обычный `<a href={PORTAL_URL}>На главную</a>`.

### 6.3. `correction-audio` (Acoustic Matcher MVP за nginx-шлюзом)

| Файл | Что делается |
|------|--------------|
| `audio-correction/mvp/static/index.html` | В шапке исходного интерфейса MVP добавить plain-анкер `<a href="https://bot-atelier.ru/">← На главную</a>`. |

Поведение:

- Переход кросс-доменный; общая cookie `session_id` не сбрасывается,
  logout не вызывается.
- Рабочая сессия MVP (`acoustic_session`) и временные файлы не удаляются:
  при возврате на `https://correction-audio.bot-atelier.ru/` состояние
  живёт в памяти контейнера до рестарта/очистки.

> Ранее ссылка размещалась в React-фронтенде
> (`audio-correction/frontend/.../AudioCorrectionPage.jsx`) вместе с
> `useNavigationGuard`; эта реализация выведена из эксплуатации.

### 6.4. Что НЕ нужно

- Не добавлять пункт «Портал» в меню подсистем как ресурс экосистемы.
- Не менять cookie, nginx-прокси или API подсистем ради этой ссылки.
- Не делать «Выход» на портале.

## 7. Риски и открытые вопросы

1. **DNS apex.** `bot-atelier.ru` сейчас указывает на `95.163.244.138`.
   Нужно перенаправить apex (и `www`) на `2.26.112.123` в reg.ru. До
   propagation certbot не выпустит сертификат. Кто и когда меняет запись?
2. **`www` vs apex.** Отдавать портал на обоих именах (проще) или
   редиректить `www → apex` (каноничнее)? Рекомендация — отдавать оба +
   `canonical`, редирект добавить позже при желании.
3. **Идентичность на портале.** Показывать имя/роль требует backend
   (HttpOnly). Сейчас — не показываем. Нужен ли backend в будущем?
4. **«Войти» при активной сессии.** `LoginPage` в `testing` не
   перенаправляет уже аутентифицированного пользователя — при клике
   «Войти» с активной сессией он увидит форму. Опциональное улучшение:
   в `testing` при наличии `user` сразу переходить на `next`/`/`.
   Требует правки `testing`, вне рамок портала.
5. **Возврат из `testing` без `next`.** При заходе на
   `testing.bot-atelier.ru` без сессии `ProtectedRoute` уводит на
   `/login` без `next`, и после входа пользователь остаётся в `testing`,
   а не на портале. Для сценария «портал → подсистема» это нормально;
   для явного входа есть кнопка «Войти» на портале с `next`.
6. **Дрейф каталога.** Список подсистем дублируется в `subsystems.js` и
   в `AGENTS.md`. Нужно поддерживать синхронность вручную; при добавлении
   подсистемы обновлять оба места.
7. **`PORTAL_URL` в `testing`.** В `correction-audio` (MVP) ссылка задана
   литералом, поэтому при смене домена править нужно в двух местах.
8. **Состояние MVP при уходе.** Уход на портал не удаляет рабочую сессию
   MVP (`acoustic_session`); состояние живёт в памяти
   `acoustic-matcher-mvp` и теряется при рестарте контейнера.
9. **Публичность портала.** Страница общедоступна; нельзя размещать на
   ней внутренние ссылки/данные. Только названия и описания подсистем.
10. **Нет аналитики/мониторинга.** Для статики это приемлемо; при
    необходимости — внешний счётчик, не встраивая сторонние скрипты в
    критичный путь.

## 8. Не в рамках текущей архитектуры

- Backend портала и показ имени пользователя.
- Личный кабинет/дашборд с агрегацией данных подсистем.
- Аутентификация на портале, собственная форма логина, собственный
  logout.
- Единая навигационная шапка как общий React-компонент (порталы и
  подсистемы — независимые деплои; шапка реализуется в каждой
  подсистеме).
- Автоматическая регистрация подсистем (каталог ведётся вручную).
